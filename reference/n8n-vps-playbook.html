n8n, one checkpoint at a time.

Read → run → inspect → stop if the evidence does not match. Keep this beside your terminal.

Companion to Lesson 4 · Ubuntu VPS · commands run on the VPS unless marked Windows

A new learning instance only.

Do not apply these files to an existing n8n installation or replace an existing proxy. No VPS commands have been executed for you. Use dummy data; installation, TLS, backup and recovery remain unverified. You need a real subdomain and control of its DNS before this route can proceed.

Checkpoint 0 — inventory before changing anything

Recall which SSH key stays on Windows, then confirm a working SSH administrator session and Hostinger recovery-console access. Keep both available. Run these read-only checks on the VPS and report only redacted results:

whoami
cat /etc/os-release
uname -m
free -h
df -h /
docker --version
docker compose version
sudo ss -lntup
sudo ufw status verbose

Confirm Ubuntu 24.04 LTS, actual available resources, port use and firewall policy rather than assuming prior lessons finished. Missing Docker or Compose? Follow Docker’s Ubuntu instructions with your teaching agent first; do not replace an existing installation blindly. Docker administration is effectively root access. Do not give the Pi/Hermes runtime accounts access to Docker to make this exercise work.

  • Ports 80/443 already occupied? Stop. Adapt the existing proxy; do not stop somebody else’s service.
  • Existing n8n data? Stop. Inventory its database, version, key and backup procedure. These are not migration instructions.
  • Low memory/disk or other agents running? Budget for all workloads and retained executions. No minimum for this smaller lab is asserted from the full AI-stack requirement.
  • No recovery access or unclear firewall? Stop before any firewall or deployment changes. Preserve SSH on its actual configured port.

Pass: you can explain the host, account, free resources, open ports, recovery route and whether this is a genuinely new instance. Nothing secret belongs in a screenshot or chat.

Checkpoint 1 — domain and guarded first login

  1. Choose a subdomain you own, such as automation.your-domain.tld. Set its A record to the VPS IPv4 address. Add AAAA only if IPv6 routing and firewall protection are verified. Preserve mail and unrelated records. Hostinger DNS guide
  2. For this lab use direct DNS, not a Cloudflare-proxied record or another load balancer. The files assume exactly one proxy, Caddy.
  3. In the provider/network firewall, preserve SSH; allow inbound TCP 80 for certificate validation and restrict TCP 443 to your current client IP during initial owner setup. Apply equivalent IPv6 protection or do not publish AAAA. Review existing allow-all rules: a narrower allow rule does not cancel a broad one.
  4. Inspect the rules now; then prove the boundary against the harmless live listener in checkpoint 3, before starting n8n. A connection failure with no listener proves nothing about a firewall. You need both an allowed-client success and a disallowed-client failure. If you cannot establish this boundary, stop and ask for an adapted private bootstrap; do not race strangers to an unclaimed setup screen.

Why not just ufw? Docker’s published ports can bypass ufw rules. Do not expose 5678. Caddy needs working DNS and reachable validation ports for automatic HTTPS. Plain HTTP on 80 redirects to HTTPS; it must not serve the owner form.

Provisional pass: DNS resolves to this server, ports are free, and the reviewed rules intend to admit only your client on 443. Live proof follows before owner setup. If your IP changes, adjust the provider rule without touching SSH.

Checkpoint 2 — inspect and prepare three files

Review the supplied compose.yml, Caddyfile and .env.example. Transfer these three files using VS Code Remote SSH or your chosen file-transfer tool to a new, private ~/n8n-lab directory on the VPS. This workspace does not automatically copy files to your host.

# On the VPS: create this directory only if it does not already exist.
umask 077
mkdir -m 700 ~/n8n-lab
cd ~/n8n-lab
# Transfer the three example files here before continuing.
cp -n .env.example .env
chmod 600 .env
openssl rand -hex 32

The last command prints a new private key. Put that value in N8N_ENCRYPTION_KEY inside .env using an editor; never paste it in chat, a ticket or Git. Do not regenerate it after first launch. Copy it into your encrypted secret backup. File permissions reduce accidental exposure; they do not encrypt Docker’s container metadata.

  • N8N_VERSION: choose an exact, supported stable tag from official n8n releases; review security notices. These files require ≥2.35.0 for N8N_WEBHOOK_URL. This floor is not a claim that any old version above it is secure.
  • CADDY_VERSION: choose an exact stable Caddy 2 tag from Caddy releases. Do not use latest for repeatable practice.
  • N8N_HOST: your real hostname only, with no scheme, slash or port.
  • GENERIC_TIMEZONE: an IANA timezone; Etc/UTC is the example. Review the workflow timezone before scheduling local-time work.

Replace every REPLACE value. Never commit .env, backups or exported credentials. If using a separate secret-free configuration repository, add those paths to its ignore rules before staging files. The stack does not mount the Docker socket, use privileged containers, or install an AI sandbox. Do not add those capabilities for this exercise.

# Run in ~/n8n-lab; -q validates without printing expanded secrets.
grep -l 'REPLACE' .env
docker compose config -q

Pass: grep prints no filename (exit 1 means no placeholders found), Compose validation succeeds, and you can point to the persistent /home/node/.n8n mount and the absence of an n8n ports mapping. Avoid sharing docker compose config without -q or docker inspect: they can reveal secrets. The example uses required-variable checks, not a full validation of hostname, versions or key quality.

Checkpoint 3 — prove the firewall, then HTTPS and owner setup

Commands use the directory and files from checkpoint 2. First pull the reviewed images and start only a harmless probe. This foreground command serves a fixed text response, not the editor, database or local files. No n8n service starts:

docker compose pull
docker compose run --rm --no-deps --service-ports caddy \
  caddy respond --listen :443 --body 'n8n firewall probe'

Keep that terminal open. On your allowed Windows client, replace the hostname below and use PowerShell. This probe deliberately speaks plain HTTP on TCP 443 to test the network boundary; send no credentials. Do not use this HTTP URL for n8n later.

curl.exe --noproxy "*" --max-time 10 http://YOUR_REAL_HOSTNAME:443/

Required evidence: the allowed client receives exactly n8n firewall probe. Repeat from a non-allowed external connection: it must fail to connect, not return that marker. Check IPv4 and any published IPv6 path independently; an untested AAAA path is not a pass. If both clients fail, the result is inconclusive. If the disallowed client succeeds, repair the provider rules and repeat. A TLS-only network filter may need an adapted probe; stop rather than infer success.

After both results match, press Ctrl-C in the probe terminal and confirm the command exits, freeing the ports. This run overrides the normal Caddy command and leaves the supplied Caddyfile unchanged. Caddy probe reference. Now, with the same firewall rules still in place, start the real services:

docker compose up -d
docker compose ps
docker compose logs --tail=60 n8n caddy
docker compose exec n8n wget -qO- http://127.0.0.1:5678/healthz
sudo ss -lntup

Inspect logs locally; redact before sharing. Expect n8n’s health endpoint to respond, Caddy to obtain a certificate, and no published host listener for 5678. This is a process check, not proof that a workflow or database restore works.

From your allowed Windows client, open https://your-real-hostname/. Verify a valid certificate for that hostname. Never bypass a certificate warning or disable secure cookies to continue. Complete owner setup immediately with a unique password; configure MFA if supported by your chosen version. After setup, check that the setup page no longer offers first-owner registration. Keep the 443 IP restriction for the initial manual exercise. n8n security guidance

Pass: valid HTTPS, owner claimed, no public 5678, health response and understood logs. The n8n docs’ full Assistant Compose file is not the topology being checked here. Caddy Compose reference

Checkpoint 4 — prove one execution and persistence

Build the Manual Trigger → Edit Fields exercise. Expect one output item containing service: practice and status: ok. Save it; inspect the execution, not just the green node.

# Only this disposable lab instance; this briefly interrupts n8n.
docker compose restart n8n
docker compose ps
docker compose exec n8n wget -qO- http://127.0.0.1:5678/healthz

Reload the editor and run the saved workflow again. This shows persistence across restart, not an independent backup. Never use docker compose down -v as cleanup: it deletes this project’s data volumes.

Pass: expected output before and after restart, saved workflow still present. Share the redacted result with your teaching agent; no completion or mastery is recorded automatically.

Optional checkpoint 5 — understand external triggers

First keep the 443 IP restriction. Duplicate the dummy workflow and replace Manual Trigger with a Webhook: POST, a unique lab path, Header Auth, and Respond → When Last Node Finishes. Keep Edit Fields set to output only the two dummy fields. Create a separate dummy header credential in n8n; do not reuse the encryption key or owner password.

  1. Select Listen for Test Event and copy the displayed Test URL. From your allowed client, use an HTTP client to send a POST with dummy JSON and the configured authentication header. Keep tokens out of shell history and screenshots.
  2. Re-arm the test listener before sending a request without that header. Expect an authentication-specific rejection and no execution, not merely a 404 or “webhook not registered” message. A consumed test listener cannot prove authentication. Editor login is not the webhook’s authentication policy.
  3. Publish the workflow and use its displayed Production URL. With valid authentication, expect the dummy fields in the response and an execution visible in Executions. Then request that same published Production URL without the header: require an authentication-specific rejection (typically 401/403), no new execution and no dummy output. A 404/unregistered response is inconclusive, not an authentication pass. A test URL outside its listening window is not a production endpoint.
  4. Only if an external service really needs access, review its authentication and source-IP needs before expanding the provider’s 443 allow rule. Do not expand it just for the manual exercise. Keep 5678 closed. This basic proxy also makes the login surface reachable by allowed callers; separating editor and webhook access is a later hardening task.
  5. Unpublish the lab webhook when done. Confirm it no longer creates executions. Do not leave throwaway ingress running.

Primary source: webhook URLs, authentication and response modes. For a schedule instead, review Schedule Trigger: choose timezone, publish, observe one run, then unpublish. UI labels can differ by pinned version.

Checkpoint 6 — backup is a second copy plus a rehearsal

For this small SQLite lab, stop n8n before copying its full data directory. Do not live-copy SQLite and assume consistency. This command block is only for this example’s named-volume layout. It creates a unique directory; stop if any command fails. Do not reuse it for Postgres or an existing installation.

# Bash on the VPS, from ~/n8n-lab. Run as one block; exit on any error.
(
set -eu
umask 077
backup="$PWD/backups/$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "$PWD/backups"
mkdir -m 700 "$backup"
docker compose stop n8n
# Bring only n8n back if archiving fails or the shell exits.
trap 'docker compose up -d n8n' EXIT
docker compose run --rm --no-deps --user 0 \
  -v "$backup:/backup" --entrypoint tar n8n \
  -czf /backup/n8n-data.tgz -C /home/node/.n8n .
sudo chown "$(id -u):$(id -g)" "$backup/n8n-data.tgz"
cp .env compose.yml Caddyfile "$backup/"
chmod 600 "$backup/"*
(cd "$backup"; sha256sum n8n-data.tgz .env compose.yml Caddyfile > SHA256SUMS)
tar -tzf "$backup/n8n-data.tgz" > /dev/null
printf 'Private backup directory: %s\n' "$backup"
)

Back up the entire directory via an encrypted transfer to encrypted storage off this VPS, under your control. It contains the credential key and sensitive database content. Verify the checksums on the second copy. Provider snapshots and a local tarball are useful but not independent recovery by themselves. Workflow JSON exports are supplementary, not a complete instance backup. Docker volume backup/restore · n8n encryption key

Rehearse offline first: use a separate private directory, restore the three matching configuration files and archive from the off-server copy, then use a distinct Compose project name such as n8n-restore. Never point it at the original volume. On a shared Docker host, project separation is storage separation, not a security sandbox. For production recovery use a separate isolated host.

# Run ONLY in the separate restore directory containing the recovered files.
# Do not run 'up': restored schedules/webhooks could cause real side effects.
(
set -eu
sha256sum -c SHA256SUMS
docker compose -p n8n-restore run --rm --no-deps --user 0 \
  -v "$PWD:/backup:ro" --entrypoint sh n8n -c \
  'test -z "$(ls -A /home/node/.n8n)" && tar -xzf /backup/n8n-data.tgz -C /home/node/.n8n'
docker compose -p n8n-restore run --rm --no-deps n8n \
  export:workflow --all --output=/dev/null
docker compose -p n8n-restore run --rm --no-deps n8n \
  export:credentials --all --decrypted --output=/dev/null
)

The empty-volume guard deliberately refuses reuse; a failed rehearsal needs inspection, not removal of the guard. Archive ownership is preserved from the original n8n data. These CLI commands do not start the workflow service or Caddy and publish no ports. The last command decrypts credentials to a sink, not a shareable file; never change it to stdout or a public path. If there are no credentials, success proves no decryption—use the dummy Header Auth credential from checkpoint 5 to exercise that check. n8n CLI export reference

Pass: off-server checksums match; a separate volume can read the database and decrypt the dummy credential with the recovered key. This is an offline recovery check, not full service recovery. Before relying on real automation, rehearse starting a recovered instance on a separate, network-isolated host with all restored triggers disabled, and verify the dummy workflow. Ask your agent to adapt that rehearsal to your host; do not run a second live copy of real automations.

Before real workflows: operations and change control

  • Health: inspect container state, health endpoint and workflow executions separately. Configure an Error Trigger/error workflow and verify a deliberately failed dummy run before depending on alerts. Watch RAM, disk, logs and execution retention; stored inputs may contain personal data. n8n error handling
  • Credentials: use least-privilege service accounts, no production keys in the first lesson. Treat community nodes as executable code and workflow inputs as untrusted. Avoid shell/Code nodes and unreviewed templates. n8n security
  • Delivery: retries can repeat external side effects. Validate payloads, deduplicate by event ID and design safe retry behavior before sending mail, charging money or deleting anything.
  • Update: read release/migration notes, take a coordinated backup, rehearse with the candidate exact tag in isolation, then change N8N_VERSION, docker compose pull n8n and docker compose up -d n8n. Verify health, login and the dummy workflow. Do not automate blind updates.
  • Rollback: migrations can change the database. An old image against a migrated volume is not a safe general rollback. Stop the affected service and restore the matching pre-update data, key/configuration and version through a reviewed recovery plan. Never overwrite the only copy.
  • Production boundary: this SQLite lab has no HA, queue workers, external task runners, SMTP setup or full access-isolation policy. Plan Postgres for important round-the-clock workloads, appropriate task-runner isolation if executing code, monitoring, retention and a complete restore drill. Merely changing DB_TYPE does not migrate SQLite data. Upstream Compose production guidance

Quick-reference glossary

Workflow / node / execution
A connected automation / one step / one run with its results.
Trigger
The event that starts a workflow: manual click, schedule or request.
Webhook
An HTTP endpoint that accepts an event. Authentication belongs to the endpoint, not merely the editor login.
Reverse proxy
The public entry point that forwards requests to a private service; Caddy in this lab.
Volume / backup
Persistent storage / an independent, recoverable second copy. Neither word implies the other.
Encryption key
The secret needed to read encrypted credentials; retain it with the matching database.
Publish
Make the workflow’s production version available to its configured automatic triggers; not the same as saving a draft.
Idempotency
Designing a repeated event so it does not repeat an unwanted side effect.

What to bring back

Start with checkpoint 0, your last successful check and your expected versus observed result. Redact tokens, keys, account details and sensitive execution payloads. Ask your teaching agent follow-up questions instead of changing random settings.
