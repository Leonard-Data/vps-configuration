Windows to Ubuntu.
One checkpoint at a time.

A companion to Lesson 2. Set up Nous Research’s Hermes Agent manually before trusting automation.

Ubuntu 24.04 LTS · Windows PowerShell · commands are examples for a fresh, dedicated learning VPS · reviewed 2 November 2026

Do not paste this whole page into a terminal.

Run one block at a time. Replace VPS_IP with your server’s literal address and YOUR_GITHUB_NAME with your GitHub username. These examples assume SSH port 22 and an initial root login supplied by your provider. If your login name, port, accounts or existing workloads differ, stop and ask for adapted commands. Nothing here has been run on your VPS.

1. Check requirements and your way back in

  • Provider recovery consoleOpen the Hostinger browser console and verify you can log in. Keep it available alongside SSH. Back up existing data before any changes. Do not reinstall Ubuntu to follow this lesson.
  • Windows toolsPowerShell, OpenSSH client, Git for Windows, VS Code and its Microsoft Remote – SSH extension. Run ssh -V and git --version; if missing, install from the official Windows/Git sources, not an arbitrary download site.
  • VPS resourcesFor this learning plan, budget roughly 2 vCPU, 4 GB RAM and 20 GB free disk; these are planning targets, not official Hermes minima. Browser tools and local models can need much more. We use a remote model provider, not a local GPU model.
  • Provider credentials and costsYou need a supported model provider/subscription or API key and an appropriate spending limit. VPS hosting does not pay for model calls.

VPS — initial administrator:

cat /etc/os-release
whoami
free -h
df -h /
ss -lnt
ufw status

Checkpoint: confirm Ubuntu 24.04, free resources, SSH’s actual port, and whether a firewall is active. A command missing or a different version means investigate, not guess. Read Hostinger’s VPS guidance and Ubuntu’s OpenSSH guidance.

2. Create a personal SSH key on Windows

Windows — PowerShell: first check for existing files. Choose a new filename if vps_learning already exists; never overwrite a key you use elsewhere.

ssh -V
Get-ChildItem "$HOME\.ssh" -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Force "$HOME\.ssh" | Out-Null
ssh-keygen -t ed25519 -a 64 -f "$HOME\.ssh\vps_learning" -C "windows-vps-learning"
Get-Content "$HOME\.ssh\vps_learning.pub"

Enter a strong passphrase when prompted. The file ending in .pub is public; the same name without .pub is private. Keep the private file on Windows. Do not paste it into chat, the VPS or GitHub.

Provider console — initial administrator: read the server fingerprint before your first SSH connection.

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

Windows — PowerShell:

ssh -o HostKeyAlgorithms=ssh-ed25519 root@VPS_IP

Compare the displayed SHA256 fingerprint with the console output. Only accept a match, then use your initial login password. If the fingerprint differs, stop; confirm the IP and ask your provider. The public-key setup comes next. Source: OpenSSH authentication and keys

3. Separate administration from the agent

We use ops to administer the server and hermes to run the agent. The agent account gets no sudo rights. The personal key can log you into both; the later CI key is separate and restricted.

VPS — initial root session: if these users already exist, do not recreate them; inspect their current configuration first.

adduser ops
usermod -aG sudo ops
install -d -m 700 -o ops -g ops /home/ops/.ssh
nano /home/ops/.ssh/authorized_keys

In nano, paste only your one-line vps_learning.pub output. Save with Ctrl+O, Enter; exit Ctrl+X. Then:

chown ops:ops /home/ops/.ssh/authorized_keys
chmod 600 /home/ops/.ssh/authorized_keys

Windows — second PowerShell window: keep the root session open.

ssh -i "$HOME\.ssh\vps_learning" ops@VPS_IP

VPS — new ops session:

sudo -v
sudo adduser --disabled-password --gecos "" hermes
sudo install -d -m 700 -o hermes -g hermes /home/hermes/.ssh
sudo install -m 600 -o hermes -g hermes /home/ops/.ssh/authorized_keys /home/hermes/.ssh/authorized_keys
sudo chmod 700 /home/hermes
sudo apt update
sudo apt install -y git curl tar build-essential libatomic1 python3

Windows — another window:

ssh -i "$HOME\.ssh\vps_learning" hermes@VPS_IP

Checkpoint: whoami should say hermes. In the ops session, id hermes must not list sudo or docker. Test both logins before closing the original session. Do not grant passwordless sudo to the agent to fix an installation error.

A folder is not a sandbox.

The agent can access what its Linux user can access, including its own credentials. Do not put other services, administrator keys or sensitive work in this account. Avoid agent access to the Docker socket: it can grant host-level control. For stronger separation, use another VPS or a reviewed sandbox.

Firewall and SSH hardening: this lab does not change your SSH port or disable authentication methods. If enabling a firewall later, allow the actual SSH port at both Ubuntu and provider layers first. Ubuntu’s OpenSSH ufw profile normally assumes port 22. Verify new logins and recovery access before disabling password/root login; validate SSH configuration with sudo sshd -t before reloading. Never delete an existing authorized key blindly.

4. Install Hermes as hermes, not root

The official installer manages its Python/runtime dependencies. Do not replace Ubuntu’s system Python or install arbitrary global pip packages to match it. At review time, first-party installs use managed Python 3.14; follow the live installer documentation if that changes.

VPS — hermes SSH session:

whoami
curl -fsSL https://hermes-agent.nousresearch.com/install.sh -o "$HOME/hermes-install.sh"
less "$HOME/hermes-install.sh"

Press q to exit less. This downloads code for inspection instead of piping it straight into a shell. Inspection is not proof of safety; the installer also downloads dependencies. Only continue if you trust the official project. For a small headless lab, omit browser/computer-use downloads:

bash "$HOME/hermes-install.sh" --non-interactive --skip-browser --skip-computer-use
source ~/.bashrc
hermes --help
hermes setup
hermes doctor

The installer’s --non-interactive flag skips its setup/service prompts; we run setup separately. Use the setup wizard to select your provider and model. Decline messaging gateway/service installation or startup for now; keep this CLI-only until the optional service step. Enter credentials in the wizard, not in a Git file or chat. Configure only the tools you need with hermes tools; disable execution tools for the first explanation-only chat. Optional tools may report missing credentials in doctor; distinguish these from a failed core installation. If installation asks for system dependencies or sudo, stop and use the separate ops account for the specific reviewed package—not a blanket privilege grant.

hermes

Ask for a plain explanation of public versus private SSH keys, without tools. Exit the chat using its documented exit command/help. Checkpoint: a model responds, billing is understood, and no agent operation needs root. Hermes CLI chat needs no public HTTP port, domain, reverse proxy or TLS certificate.

Secrets: treat all of ~/.hermes/ as private. Config, tokens, sessions and memories can be sensitive. Do not run git init there or upload the entire directory. Official configuration reference

5. Prepare a development environment

Windows: install Git for Windows and VS Code Remote – SSH. In VS Code choose “Remote-SSH: Open SSH Configuration File” and add these entries to your Windows ~/.ssh/config, replacing the placeholders:

Host vps-ops
    HostName VPS_IP
    User ops
    IdentityFile ~/.ssh/vps_learning
    IdentitiesOnly yes

Host vps-hermes
    HostName VPS_IP
    User hermes
    IdentityFile ~/.ssh/vps_learning
    IdentitiesOnly yes

Windows — PowerShell checkpoint: run ssh -G vps-ops to check that the local configuration can be read, then ssh vps-ops to test a real connection. Exit the test session before continuing. If OpenSSH reports bad owner/permissions on ~\.ssh\config or an unrecognized SID, follow the local Windows config repair below before retrying VS Code. A local config rejection is not a reason to change the VPS firewall.

Use “Remote-SSH: Connect to Host” → vps-ops. Create ~/projects/hermes-ops in the VS Code terminal and open that folder:

mkdir -p ~/projects/hermes-ops
cd ~/projects/hermes-ops

This keeps development under ops, apart from /home/hermes. It is suitable for editing the lab’s text files, not an isolated second server. Do not run the agent as ops, edit live credentials through the repository, or test destructive tools on this machine. The examples manage instructions, not Hermes source development; use a separate account/VM for a second full runtime.

For this small repo, editing locally on Windows is also fine. If VS Code is remote, Git commands in its terminal run on the VPS, while a local PowerShell terminal runs on Windows. Keep that distinction visible.

Connecting from another computer or to another VPS

SSH setup is local to each client computer. Creating a key and config on your first Windows computer does not configure a second laptop, desktop or Windows account. The same workflow applies, but each machine has its own paths, account permissions and trusted-host records.

  1. New computer → the same VPSRepeat the local key-generation step on the new computer with a fresh, passphrase-protected personal key. Use a descriptive unused filename such as vps_learning_laptop; never overwrite an existing key. Do not copy your private key, CI key, or the whole .ssh folder from the first machine.
  2. Authorize the new public key without removing the old oneKeep your working login/recovery console open. Through that trusted session, append the new machine’s complete .pub line to ~/.ssh/authorized_keys for each VPS account it needs: ops, and separately hermes if needed. Preserve all existing entries, file ownership and restrictive permissions. Do not rerun account creation or a file-copy command that replaces authorized_keys. Grant access only to machines and users you trust.
  3. Configure and verify the new client independentlyCreate or merge the two Host entries above into that computer’s local config. Update IdentityFile to its new key filename; ~ means the home of the user on this computer, not the VPS. Recheck the local file owner/permissions: Windows SIDs are account-specific, so do not reuse an ACL backup or stale SID from another machine. On a first connection, verify the VPS host fingerprint against the recovery console again; do not blindly copy known_hosts or disable host-key checking.
  4. Prove the second machine works before retiring the firstOn the new client run ssh -G vps-ops, then ssh vps-ops; test vps-hermes too if authorized. Only then try VS Code Remote-SSH. Do not remove the first computer’s public-key entry until the new login and recovery access work. If a device is lost, revoke its exact public-key line from every account/server that trusted it; deleting its local config does not revoke access.

Another VPS: add distinct aliases such as vps2-ops and vps2-hermes, using that server’s actual HostName, User, IdentityFile and Port if it is not 22. Provision/authorize the intended accounts on that server, verify its own fingerprint, and test each alias separately. The first VPS’s addresses, account setup and host keys are not transferable. Replace vps-ops in the verification commands with the alias you are testing.

macOS/Linux clients: the same SSH config fields work, but use that OS’s terminal and permission tools—not Windows PowerShell ACL commands. Keep ~/.ssh accessible only to its owner and config/private-key files owner-only (typically directory mode 700 and file mode 600). On shared or managed computers, ask the administrator before changing ownership or permissions. Never store personal private keys on an untrusted shared computer.

6. Create your own small repository

Create an empty private repository named hermes-ops on GitHub (do not initialize it with a README). Private does not mean safe for secrets. We use GitHub HTTPS authentication for Git; it is distinct from your VPS login key.

In your development folder, copy these downloadable examples into the exact paths below. Keep the dot-prefixed names. Your browser may suggest a different filename; correct it.

  • SOUL.md — reviewed, non-secret identity instructions.
  • .gitignore — accident prevention, not secret scanning.
  • deploy_soul.py — bounded, single-file deployment handler.
  • .github/workflows/deploy.yml — CI and gated delivery. Do not add it yet if skipping the optional lab.

If editing remotely, download on Windows first and drag the files into the VS Code remote Explorer. Make the nested .github/workflows folders if using the lab.

hermes-ops/
  .gitignore
  SOUL.md
  deploy_soul.py
  .github/workflows/deploy.yml   # optional lab only

VPS — ops, VS Code terminal in ~/projects/hermes-ops:

git init -b main
git config user.name "YOUR_NAME"
git config user.email "YOUR_GITHUB_NOREPLY_EMAIL"
python3 deploy_soul.py --check < SOUL.md
git add .gitignore SOUL.md deploy_soul.py
git diff --cached
git commit -m "Add reviewed Hermes learning instructions"
git remote add origin https://github.com/YOUR_GITHUB_NAME/hermes-ops.git
git push -u origin main

Use the HTTPS authentication flow provided by your Git tooling. GitHub account passwords do not authenticate Git pushes; use Git Credential Manager/browser login locally, or a least-privilege, expiring token when a remote terminal requires one. Enter a token only at the password prompt; never embed it in the remote URL or save it in a file. Remote HTTPS push troubleshooting: GitHub remote authentication. Do not turn on SSH agent forwarding to work around this.

Checkpoint: GitHub shows only your intended files. A .gitignore cannot remove an already-tracked secret from history. If a credential leaks, revoke/rotate it immediately, then clean history as needed. GitHub secret-removal guidance

7. Optional: keep a messaging gateway running

Skip this for CLI-only learning. A background gateway is useful for messaging, not a prerequisite for chatting over SSH. First run hermes gateway setup as hermes and configure only the platform you use. Set the platform’s allowed-user controls to your own account before starting it; keep bot tokens private. Follow the official messaging guide.

We choose a user systemd service plus linger, avoiding a root-run agent. Do not also install a system service. VPS — ops:

sudo loginctl enable-linger hermes

VPS — direct SSH login as hermes:

hermes gateway install
hermes gateway start
hermes gateway status
journalctl --user -u hermes-gateway -n 50 --no-pager

Checkpoint: send a message from your allowed account and receive a reply; check a disallowed account cannot invoke it. Log out, reconnect, then check status again. Later verify after a planned reboot, not while important work is running. Logs may contain private content; redact before sharing. No public inbound web port is needed for CLI or ordinary polling-based bot use; other integrations may differ.

8. Optional lab: approved automatic instruction deployment

Scope: one file, not the whole application.

This lab replaces /home/hermes/.hermes/SOUL.md and preserves one previous version. It does not update Hermes binaries, send API keys, deploy sessions, or restart the gateway. A new identity replaces the built-in default; review it carefully. Start fresh conversations to test changes; existing gateway sessions may need a controlled restart/new session.

A. Install the restricted handler once

Read deploy_soul.py. It accepts UTF-8 Markdown beginning with # , at most 16 KiB, and writes only the fixed SOUL path. The copy on the VPS is installed separately; future repository changes do not silently change the server’s handler.

VPS — ops:

cd ~/projects/hermes-ops
python3 deploy_soul.py --check < SOUL.md
sudo install -o root -g root -m 755 deploy_soul.py /usr/local/bin/deploy-hermes-soul
sudo -u hermes /usr/local/bin/deploy-hermes-soul < SOUL.md

The last command is your first manual deployment. Stop and read errors. As hermes, start a fresh chat to check the intended response style before automating it. The handler is root-owned but runs as hermes; no sudo is granted to CI.

B. Create a dedicated deployment key

Windows — PowerShell: use a new filename, not your login key. For this noninteractive CI key only, press Enter twice for an empty passphrase. Its private half must be stored as an Actions environment secret.

ssh-keygen -t ed25519 -f "$HOME\.ssh\hermes_ci" -C "github-hermes-soul-only"
Get-Content "$HOME\.ssh\hermes_ci.pub"

VPS — ops: open the agent’s authorized keys without removing its existing login key.

sudo nano /home/hermes/.ssh/authorized_keys

Add one separate line below the personal key, substituting the full public deployment key. Do not add the private key. There must be no line break between the restriction and ssh-ed25519:

restrict,command="/usr/local/bin/deploy-hermes-soul" ssh-ed25519 REPLACE_WITH_PUBLIC_KEY_BODY github-hermes-soul-only

restrict disables forwarding, PTY and related features. The forced command ignores any requested shell command and processes stdin as the one allowed file. A stolen key can still change agent instructions: this restriction reduces SSH scope, not the impact of malicious prompts. Keep this on a dedicated learning account. OpenSSH authorized-key options

C. Pin the server identity

Provider recovery console:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
cat /etc/ssh/ssh_host_ed25519_key.pub

Build a known-hosts line from the console-verified public host key (do not invent or copy this placeholder):

VPS_IP ssh-ed25519 REPLACE_WITH_SERVER_HOST_PUBLIC_KEY_BODY

This is the server’s host key, not your user’s public login key. Use the exact same IP/hostname that Actions will connect to. Do not collect it with an unverified ssh-keyscan during deployment. These examples only support SSH port 22; a custom port also changes the known-hosts entry format and the workflow.

D. Configure GitHub’s gate and secrets

In the GitHub repo, open Settings → Environments → create production. Add required reviewers and restrict deployment branches to main. Enable prevention of self-review if someone else can approve your changes. Do not assume these controls exist on every GitHub plan: availability differs for private repositories. If required reviewers are unavailable, keep the workflow out of the repo and continue manual deployment; do not claim a manual gate exists. GitHub environment availability and protection rules

Add these environment secrets, not plaintext files:

VPS_HOST
The literal server IP/hostname, matching the known-hosts line.
VPS_KNOWN_HOSTS
The single verified host-key line from C.
VPS_DEPLOY_KEY
The entire private hermes_ci file, including BEGIN/END lines. Never the personal ops key.

Keep a protected backup of the private deployment key if needed; once the secret is stored, remove disposable plaintext copies. Anyone controlling the approved workflow can use its secrets. Protect main with reviewed pull requests and require the CI check where your GitHub plan supports it. The example uses major action tags for readability; production pipelines should pin actions to reviewed full commit SHAs.

E. Add the workflow and make one harmless change

Save the downloaded workflow at .github/workflows/deploy.yml. Read it before committing. CI uses Python already installed on the Ubuntu runner; no third-party SSH deployment action is needed.

VPS — ops, development folder:

git add .github/workflows/deploy.yml
git diff --cached
git commit -m "Add checked and approved SOUL delivery"
git push

In GitHub’s Actions tab: verify the format check succeeds, inspect the proposed commit, then approve the waiting production job. After successful transfer, open a fresh Hermes session and test the behavior. Deployment success only proves a file was written; it does not prove a model call or gateway is healthy.

For subsequent practice:

git switch -c practice-clearer-instructions
# Edit SOUL.md in VS Code; do not add secrets.
python3 deploy_soul.py --check < SOUL.md
git add SOUL.md
git diff --cached
git commit -m "Clarify learning instructions"
git push -u origin practice-clearer-instructions

Open a pull request on GitHub. Check the proposed text and CI result, then merge. The production approval gates the automatic file transfer. Do not run untrusted pull-request code with production secrets or use pull_request_target to bypass this separation. CI checks format, not harmful intent; a human must review instructions.

Network stop point: GitHub-hosted runners must reach SSH. Do not open all inbound ports or remove an existing SSH allowlist just to make this work. If your VPS permits only your home IP, keep manual deployment or design a private deployment path with help. Never install a general self-hosted Actions runner under the production agent account as a shortcut.

9. Rollback, updates and backups

VPS — hermes, only after a successful deployment created the previous file:

test -f ~/.hermes/SOUL.md.previous && \
  cp -p ~/.hermes/SOUL.md.previous ~/.hermes/SOUL.md

Then start a new conversation and retest. If using the gateway, plan a restart as hermes with hermes gateway restart and check status/message delivery afterward. For a durable rollback, also revert the bad repository commit using a reviewed pull request; otherwise a later deployment can reapply it.

The lab preserves one previous file only, not an independent backup or a release history. A failed validation leaves the current file unchanged; a failed disk write should be investigated before retrying. Do not run simultaneous manual and CI deployments.

Hermes application updates are separate: review official update guidance, take a protected backup and note the installed version/commit, then run hermes update as hermes during a maintenance window. Test CLI and gateway afterward. Do not use git pull main plus blind restarts as a production update policy. We do not automate binary updates in this beginner lab.

Back up private configuration, required credentials and application state to a separate encrypted location, using the current official export/import guidance and a tested restore process. A Git repository of SOUL.md is not that backup. A profile export may exclude credentials. Never push a backup archive to this repo or paste it into chat. See the VPS backup reference.

10. Troubleshoot the smallest failing layer

SSH times out
Check the correct IP/port, network, provider firewall and SSH listener from the recovery console. Do not disable every firewall.
Permission denied (publickey)
Check the username, explicit -i key path, one-line public key and file ownership/modes. ssh -v shows which key is offered; redact usernames/addresses before sharing diagnostics. Never post the private key.
Host key changed
Stop and independently verify the console fingerprint. A rebuild can change a host key, but an attack or wrong IP can too. Do not blindly remove the old known-host entry.
hermes: command not found
Reconnect as hermes, run source ~/.bashrc, and inspect installation output/PATH. The ops and hermes accounts have different homes.
No model reply
Run hermes doctor; check provider setup, quota, outbound network and billing without printing credentials.
User systemd bus unavailable
Use a direct SSH login as hermes, not just sudo su. Have ops verify linger. Do not run the agent as root to hide a session problem.
Actions deployment fails
Check environment approval, the exact secrets, reachable SSH, pinned host key and forced-command file. No reviewer prompt means protection may be missing, not that approval succeeded.

Windows rejects .ssh\config before connecting

Symptom: Windows OpenSSH rejects your local ~\.ssh\config because its permissions include an unrecognized account/SID. In this reported failure, the connection stops locally before reaching the VPS. VS Code’s UnparsableOutput is a follow-on error: Remote-SSH never got to run its remote setup script. That error can have other causes; check the first SSH error in the Remote-SSH output rather than assuming every parsing error is an ACL problem.

Windows — local PowerShell, as the same Windows user who runs VS Code: close connection attempts. This repair and its checks target the default $HOME\.ssh\config. Confirm that Remote-SSH’s output names that file. If it names a custom config path, stop and have that separate configuration reviewed rather than applying these default-file checks. Do not run these commands in the VPS terminal.

$config = Join-Path $HOME '.ssh\config'
whoami /user
(Get-Acl -LiteralPath $config).Owner
icacls "$config"

Confirm that the file belongs to your current Windows account and that the SID named in the SSH error appears in its access list. A SID is an account identifier, not an SSH key. An unrecognized SID can be left over from an old account; do not delete arbitrary entries just because they look unfamiliar. If the owner is wrong, this is a managed/work computer, or you cannot identify the offending entry, stop and ask the device administrator to repair this one file’s ownership/ACL.

Repair only the SID named in the error. Replace the placeholder below with its exact S-1-… value. Save the current access list first. Disabling inheritance with /inheritance:d copies existing inherited entries, keeping your current access; removing the offending entry then works even if it was inherited.

$badSid = 'REPLACE_WITH_SID_FROM_YOUR_SSH_ERROR'
if ($badSid -notmatch '^S-1-[0-9-]+$') { throw 'Replace the SID placeholder first' }
if ($badSid -eq [System.Security.Principal.WindowsIdentity]::GetCurrent().User.Value) {
    throw 'Do not remove your own Windows account; ask for help'
}
$aclBackup = Join-Path $HOME ("ssh-config-acl-{0}.txt" -f (Get-Date -Format 'yyyyMMdd-HHmmss'))
icacls "$config" /save "$aclBackup"
if ($LASTEXITCODE -ne 0) { throw 'ACL backup failed; stop' }
icacls "$config" /inheritance:d
if ($LASTEXITCODE -ne 0) { throw 'Inheritance change failed; stop' }
icacls "$config" /remove "*$badSid"
if ($LASTEXITCODE -ne 0) { throw 'SID removal failed; stop' }
icacls "$config"

The leading * tells icacls to use a numeric SID. These commands affect only this config file, preserve other existing entries and do not rewrite its host settings or private keys. Keep the ACL backup for recovery with an administrator; do not blindly restore the insecure ACL. If any command says access denied, stop rather than recursively resetting .ssh, granting Everyone access, or running VS Code as administrator.

Verify locally, then remotely:

ssh -G vps-ops > $null
if ($LASTEXITCODE -ne 0) { throw 'Local SSH config is still rejected; stop' }
ssh vps-ops

ssh -G evaluates the local configuration without connecting; it does not prove network reachability or authentication. The real SSH login is the second gate. Once it works, exit the SSH session and reconnect with VS Code. If OpenSSH reports another unauthorized entry or bad ownership, the targeted repair was not enough: have the file’s owner/ACL reviewed against the OpenSSH rules. Do not work around the checks by bypassing the config, changing server permissions or reinstalling the remote VS Code server.

Sources: Win32-OpenSSH client config security · Microsoft icacls reference · VS Code Remote-SSH troubleshooting. This recovery path is source-checked, not executed on your Windows machine.

Keep these boundaries nearby

Personal login key
Windows private key + server public key; passphrase-protected, interactive access.
Host key
Server identity; verify independently, then pin in known_hosts.
Deployment key in this lab
A separate SSH user key restricted to one command; not a GitHub repository deploy key.
Repository
History of reviewed non-secret files. Not the live Hermes home.
CI / delivery gate / CD
Check the commit / approve the release / transfer the file automatically.
Service / health
A supervisor keeps a process running; a real test message verifies useful behavior.

Your evidence checklist

  • Recovery console works; ops and hermes SSH keys work in fresh sessions.
  • The agent runs without sudo and can answer a harmless question.
  • The repository contains no tokens, keys or private agent state.
  • If you did the optional lab: CI checks, approval actually blocks delivery, one reviewed file changes, and a rollback is rehearsed.
  • No HTTP port, domain, Docker stack or full binary-upgrade automation was added unnecessarily.

Ask your teaching agent about any step you cannot explain. Review the three recall questions tomorrow and again next week. Reading this playbook is not proof of operational mastery.
