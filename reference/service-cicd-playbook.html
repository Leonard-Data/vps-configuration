Service CI/CD playbook.

First automate a harmless configuration change. Promote application updates only after the boundary is real.

Reference for Lesson 6 · required approval for every deployment

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Checkpoint 0 — choose what you are delivering

First working lab: reuse the restricted SOUL.md CI/CD setup and its downloadable workflow. It validates and delivers one configuration file with one prior copy. It does not install or upgrade Hermes, Pi or n8n and is not a full backup.

Service-version delivery: this reference is a design/rehearsal checklist, not a ready-to-run application updater. Complete the manual service procedure first. Do not turn the old lab’s file-copy key into a general shell or grant it Docker/sudo access. This workspace has no remote repository or live pipeline configured by the teacher.

Keep secret-free desired versions and procedures in a reviewed Git repository. Keep credentials, private state and backups elsewhere. Separate identities: your login key, the limited deployment key and the server’s host key are different things.

Checkpoint 1 — CI checks without production access

Open a pull request for one target change. CI should reject a moving version (latest), unresolved placeholders, changes outside the allowed service and known secret files. Check Bash syntax, parse YAML, validate the inventory schema, and compare changed files with the expected scope. A human still reviews secrets and operational intent: a filename allowlist is not a complete secret scanner.

For the existing SOUL lab, the real check is:

# Local checkout or isolated CI runner — never a production agent home.
python3 deploy_soul.py --check < SOUL.md

For n8n, validate a dummy configuration using docker compose config -q in an isolated runner with no production key. Do not use production credentials to validate a pull request. Parsing is not a migration rehearsal. For Pi, check the selected package and factory compatibility in a disposable environment. For Hermes, test the selected release/update channel and preserve evidence from a lab with no live messaging. Always review each target’s release notes.

Pin external Actions to reviewed full commit SHAs in production. Do not expose production secrets to untrusted pull-request code, pull_request_target jobs executing PR content, or a general self-hosted runner on the VPS. GitHub secure-use guidance

Checkpoint 2 — prove approval before adding secrets

  1. Create a GitHub environment named production deliberately. Add required reviewers, restrict allowed deployment branches to reviewed main, disable bypass where supported and prevent self-review when independent approval is required.
  2. Check plan availability. Required reviewers on Free/Pro/Team are available only for public repositories. Other protection features have their own availability. If your private repository cannot enforce the chosen gate, retain manual deployment; do not make a secret-bearing repo public.
  3. Run a harmless environment-bound job with no deployment secrets. Confirm it waits for approval. Reject it and prove no deployment step ran. Rerun and approve the exact reviewed commit.
  4. Only after that proof add the limited key and verified known-hosts line as environment secrets. A missing/misspelled environment may be created automatically without protection—its presence in YAML is not proof of a gate.

A manual workflow_dispatch trigger is a launch control, not an independent reviewer. Branch restrictions and code review protect the workflow itself; a compromised reviewed workflow can misuse its secrets. Environment behavior, availability and automatic creation

# Teaching fragment — NOT a complete deploy workflow.
# A CI job named check must validate the reviewed change first.
on:
  workflow_dispatch:
permissions:
  contents: read
concurrency:
  group: production-service-maintenance
  cancel-in-progress: false
jobs:
  deploy:
    needs: check
    environment: production
    runs-on: ubuntu-latest
    steps:
      # Required reviewers are configured in Settings, not in this YAML.
      # No SSH step belongs here until the server handler is reviewed.
      - run: exit 1  # Deliberate stop: build the service-specific boundary first.

The fragment deliberately fails closed and lacks the referenced check job: it is a diagram in YAML, not a file to commit. Use the complete configuration-only lab to learn Actions mechanics. A service updater needs the boundary below before any SSH step.

Checkpoint 3 — the application deployment boundary

The server must independently constrain what the key can do. A forced command in authorized_keys ignores requested shell commands and invokes one reviewed handler. The handler must not concatenate SSH_ORIGINAL_COMMAND, branch names, package specs or user input into a shell.

Required contract before automating application changes
BoundaryRequired behavior and rejection test
Identity / privilegesDedicated limited account, administrator-owned handler, no unrestricted sudo/Docker/socket access. A requested shell must not execute.
Immutable requestBind approved commit, service, exact reviewed target and procedure. Reject mutable branch references, unknown services and arbitrary URLs/options.
Server lock / driftRefuse parallel manual or CI operations. Verify expected installed version and project/volume identity before mutation.
Backup evidenceRequire fresh coherent off-server backup and isolated restore evidence for this target. Abort before mutation if absent.
Health / failureApply one service, verify actual version plus harmless application behavior, record a redacted receipt. Nonzero health failures stop delivery; no success stamp or blind automatic database rollback.

Hermes needs a release-specific source/runtime plan; Pi needs its owner’s intended Node/npm context; n8n needs a tightly bounded privileged helper and migration-aware state protection. These are separate adapters, not one shell command. Building and securing them is a later implementation task after a manual rehearsal; ask for a review rather than improvising root automation.

At the SSH client boundary use verified host identity and an explicit key:

# Shape only: requires protected key, verified known_hosts and reviewed handler.
# Do not run until the server boundary and approval gate have been proven.
ssh -o BatchMode=yes -o IdentitiesOnly=yes -o ForwardAgent=no   -o StrictHostKeyChecking=yes -o UserKnownHostsFile=known_hosts   -i deploy_key deploy@REPLACE_WITH_VERIFIED_HOST

This intentionally requests no arbitrary command; the server’s forced command owns the operation. The command is illustrative, not a deployment implementation. Build known_hosts from an independently console-verified host key, not an unchecked runtime ssh-keyscan. Keep SSH firewall restrictions; if hosted runners cannot reach the existing allowed path, keep manual deployment or design a private path. Never remove the allowlist just to get green CI.

cancel-in-progress: false avoids killing a deployment when a newer run arrives, but GitHub concurrency is not a full FIFO queue and can replace pending runs. It is not a server lock and cannot coordinate a human terminal. Verify the reviewed commit again at approval. GitHub concurrency semantics · OpenSSH restrictions

CI/CD troubleshooting

Failure is a stop signal
SymptomCheckDo not
No approval promptExact environment spelling, required reviewers, plan, branches and bypass settingsTreat workflow_dispatch as approval or add secrets before gate proof
Job stays pendingApproval request, concurrency group and runner availabilityCancel an in-flight migration merely to start another
Host key verification failedRecovery-console fingerprint and known-host hostname/portUse StrictHostKeyChecking=no
Permission denied (publickey)Dedicated account/key, authorized_keys mode and forced-command pathPaste a private key into logs or swap in your administrator key
SSH timeoutExisting approved network route, listener and firewallOpen all ports or install an unrestricted runner on production
Wrong version / changed stateRequest commit, expected prior version, locks and receiptsContinue through drift or mark the target deployed
SSH passed, app unhealthyService-specific health check and private logsClaim success from SSH exit alone or blindly revert an image after migration

Checkpoint 4 — evidence to bring back

Show a secret-free CI result, approved commit identity, rejected-gate rehearsal and service-specific manual receipt. Ask your teaching agent follow-up questions before designing the privileged deployment adapter. No learning record should claim deployment mastery from reading YAML.
