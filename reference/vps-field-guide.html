The VPS field guide.

Know what each layer does, what can go wrong, and what evidence makes a setup trustworthy.

Reference, not a single sitting’s lesson · Browser Print → Save as PDF · Reviewed 2 November 2026

Read before acting

This guide does not inspect your server. Actual OS, SSH port, template, firewall rules and backup entitlements are unknown. Commands below are observational examples for an Ubuntu/Linux learning environment, not an installation script. Never paste passwords, API tokens or private keys into this page or chat.

OS: the foundation you maintain

The operating system manages processes, users, memory, disks and networking. A distribution such as Ubuntu or Debian bundles the Linux kernel with packages and maintenance tools. A provider template may add Docker or a control panel on top.

Choose for your learning goal
ChoiceWhat you gainWhat you still own
Plain supported OSA small starting point; learn each service you add.Package updates, access control, service setup and recovery.
Docker templatePreconfigured container tooling; quicker path to Compose.The host OS, image updates, published ports, secrets and data.
Control-panel templateA GUI for selected hosting tasks.Panel security, licensing if applicable, and everything outside its scope.

Suggested default, not a verified requirement: a supported Ubuntu LTS release is a reasonable beginner learning target. Confirm the application’s requirements and Hostinger’s current template compatibility first. If your VPS already works, inventory it rather than reinstalling just to match a tutorial.

Reinstall is destructive.

Changing the OS/template can permanently erase current data and the manual snapshot. Export important files and application-consistent database backups independently before considering it. A panel or Docker Manager installation is not a reason to blindly replace a live OS.

Sources: OS selection · OS change and reinstall.

Security: reduce who can do what

Think in boundaries: provider account → SSH access → host permissions → network listeners → application accounts. Hardening one boundary does not secure the rest.

  • Provider account: enable available multi-factor authentication, secure recovery methods, and protect API tokens. Someone with account access may be able to reset or destroy the server.
  • SSH: use a named administrator and key-based login. Your public key goes on the server; your private key stays private. Check the server’s host-key fingerprint through a trusted provider/recovery channel instead of ignoring identity warnings.
  • Least privilege: use elevated privileges only when necessary. Do not treat membership of the Docker administration group as ordinary unprivileged access.
  • Updates: maintain the host and application/container images. Plan restarts and reboots, then verify services recovered.
  • Network: allow only intended traffic. Usually public web traffic reaches 80/443, administration is restricted, and databases stay private. Your actual requirements may differ.
  • Secrets: keep passwords and tokens out of Git, screenshots, image builds and public frontend bundles. Protect the files or secret store supplying them.

A safe access-change sequence

  1. Confirm provider console or recovery access first.
  2. Keep the current SSH session open. Prove the new account/key works in a second independent session.
  3. Check SSH configuration syntax before restarting its service. Account for included configuration snippets, not just the main file.
  4. After the change, prove a fresh login still works. Only then close the old session.
  5. When changing firewall rules, permit the actual SSH port/source before applying a restrictive policy. Re-test externally, including IPv6 if enabled.

On Ubuntu, sudo sshd -t checks syntax; no output and a zero exit status indicate the syntax check passed. That does not prove you can log in. This guide deliberately does not give a blanket “disable passwords” or “enable firewall” command.

Docker changes the firewall picture.

Published container traffic can bypass ufw’s usual rules. Check host bindings and provider firewall policy, and test allowed and denied connections from another machine. Do not disable Docker’s firewall integration as a shortcut.

Sources: Ubuntu OpenSSH safety · Docker firewall behavior. Least-privilege, account protection and external testing are operational recommendations.

Docker Manager: convenience over the same machinery

An image packages application files and dependencies. A container is a running instance. Compose describes services, networks, volumes and settings in YAML. Hostinger’s Docker Manager provides a UI for deploying those projects; it does not replace the host OS or your responsibility for the configuration.

The provider guide describes manual Compose, deployment from a URL, and catalog deployment. It requires the supported Docker template. If your current template differs, investigate support before changing it—template replacement may erase data.

Review a project before clicking Deploy

  • Image: who publishes it? Use a deliberate version or digest and a planned update process rather than blindly following a changing tag.
  • Ports: what host address and port are published? Does this service need public reachability?
  • Data: what survives replacement, and how will it be backed up?
  • Secrets: where do credentials come from, and who can read them?
  • Privileges: reject unexplained privileged mode, host mounts and access to the Docker socket.
  • Operations: define health checks where appropriate, restart behavior, resource use, and bounded log growth.
# Illustrative Compose port fragment — NOT a complete project
ports:
  - "127.0.0.1:8080:80"
# host loopback : host port : container port

This IPv4 loopback binding is for a service intended to be reached from the host, for example by a host-based proxy. It is not a universal secure deployment recipe. A proxy in another container should normally reach the service over a private Docker network, not that container’s own 127.0.0.1. Review all bindings and verify external exposure.

Replacing a container should not replace your only copy of the data. Named volumes persist independently, but commands such as docker compose down -v can delete volumes. Do not experiment with cleanup on irreplaceable data.

Sources: Containers · Hostinger Docker Manager · Volume lifecycle · Port exposure.

DNS locates. TLS protects. Your app responds.

DNS maps names to records. It does not deploy your application, open the firewall, select a container port or issue a certificate.

The records you will meet first
TermMeaningIllustrative value
AA name points to an IPv4 address.app.example.com → 203.0.113.10
AAAAA name points to an IPv6 address.Only configure after proving IPv6 works.
CNAMEA name aliases another name, not an IP address.www.example.com → app.example.com
TTLHow long a record may be cached, in seconds.300 means five minutes, not instant change everywhere.
NameserversIdentify who hosts authoritative DNS for the zone.Change records at that authority.

The example domain and IPv4 address are documentation placeholders, not a real destination. Start with an unused subdomain so you do not disturb an existing site or email setup. Preserve unrelated records, especially mail-related MX and TXT entries. A stale AAAA record can send IPv6 clients to the wrong server even if the A record is correct.

TLS/HTTPS: after DNS and routing work, provision a certificate for the hostname, ensure the TLS listener is reachable, and verify automatic renewal. A valid certificate encrypts the connection and authenticates the hostname; it does not make application code safe or replace login controls.

Why a DNS change is not immediately visible everywhere

Resolvers may still hold old answers until their previous TTL expires. Editing the TTL now does not shorten copies already cached under the old TTL. Check authoritative answers as well as a client resolver before repeatedly editing records.

Sources: Hostinger domain pointing · RFC 1035: A, CNAME and TTL · RFC 3596: AAAA. TLS setup depends on your chosen proxy; select its official guide before implementation.

APIs: two meanings, two sets of permissions

Do not confuse the control interface with the workload
InterfaceWhat it doesSecurity boundary
Provider management APIAutomates Hostinger resources, including supported VPS and DNS operations.A provider token can authorize real account actions.
Application APIExposes your application's behavior: for example, reading a task list.Your application must authenticate and authorize requests as needed.

Hostinger’s API uses Authorization: Bearer YOUR_API_TOKEN. A bearer token is a credential, not a harmless identifier. Generate it in the provider’s API area, keep it server-side or in a protected automation secret store, and revoke it if exposed. Do not put it in this HTML or browser-side JavaScript.

First practice: identify a documented read-only operation. Inspect its permissions, response shape and rate limits. Never test delete, reinstall or restore operations just to see what happens. The API explorer can affect your real account.

For an application API, a response from /health is only an example convention: your application may not implement it, or it may check only the web process and not the database. Check documented behavior before relying on it.

Primary source: Hostinger API documentation. Endpoint behavior and token capabilities must be checked against the current reference.

Monitoring: “running” is not “working”

Use several signals. Provider graphs tell you about the machine; an external request tells you what a user can reach. Logs help explain why something failed.

A small useful monitoring plan
SignalQuestion it answersFirst action
CPU and RAM trendIs the workload approaching capacity?Compare with normal load and recent changes; one spike is not a diagnosis.
Disk and inode useWill writes or logging stop?Find the growing files; do not blindly prune volumes.
External uptime and latencyCan a user reach a useful response?Check DNS, TLS, network and then application behavior.
Application/service logsWhat happened around the failure?Correlate timestamps, errors and deployment changes; redact secrets.
Backup freshness and restore testIs recovery still possible?Investigate missed copies or failed restores before assuming protection.

Hostinger’s guide places resource graphs under VPS → Manage → Backups & Monitoring → Server Usage; labels can change. Track CPU, RAM, disk and traffic there. An external monitor should run outside this VPS so it can report when the VPS itself is unavailable.

Observational examples, not installation steps

# Run on the VPS, after confirming it is Linux:
cat /etc/os-release      # distribution and version
uptime                   # uptime and load averages, not CPU percentage
free -h                  # memory overview
df -h                    # filesystem space
df -i                    # inode use
ss -lnt                  # TCP listening addresses and ports
# Only if Docker is already installed and you have permission:
docker ps                # running containers; not proof of app health

A listening socket does not prove internet reachability. docker ps does not prove database availability. Inspection output can reveal internal details; redact it before posting. Do not blindly add sudo if a command fails—understand the permissions first.

A complete alert has an owner and an action. Start with unavailability, sustained disk pressure and failed backups. Set capacity thresholds from your baseline and response time, not an arbitrary copied number. Test that a notification actually reaches you.

Source: Hostinger resource monitoring. Multi-layer checks, alert response and external monitoring are operational recommendations.

Backup: prove you can get back.

A backup is useful when it can restore the data you need, within the time you can afford. Decide two things before choosing a schedule:

  • RPO — recovery point objective: how much recent data can you afford to lose? A nightly copy can lose roughly a day of changes if it is the latest usable recovery point.
  • RTO — recovery time objective: how long can the service be unavailable? Downloading, reinstalling, restoring and verifying all consume time.
Three tools that are not interchangeable
ToolUseful forDo not assume
Docker volumeData surviving container replacement.It survives host loss, accidental deletion or corruption.
Provider snapshot / VPS backupWhole-server rollback or recovery, within provider limits.It is an independent archive forever, or safe to restore over new data.
Independent application backupPortable copies of data and configuration stored away from the VPS.It works until you test decrypting and restoring it.

At review time, Hostinger’s backup guide describes weekly automated backups by default, optional paid daily backups, and a single manual snapshot expiring after one day. Confirm your plan, actual recovery points and current retention. A snapshot is a temporary change checkpoint, not your only long-term protection.

Full-server restore overwrites the current server.

Preserve newer data separately first. The provider guide says restore cannot be undone or canceled. Do not practice restoring over your only valuable VPS. Direct downloads of provider backups/snapshots are not supported by that guide; independent file transfers and database exports are a separate backup workflow.

Your smallest credible recovery plan

  1. List what matters: database, uploaded files, Compose/configuration and required secrets. Keep credentials out of public repositories and protect their recovery copy.
  2. Create a database-consistent backup using your database’s documented procedure. Copying live database files indiscriminately can produce an unusable backup.
  3. Store an encrypted independent copy outside the VPS; consider account separation, access restrictions and retention that survive accidental deletion or compromise.
  4. Restore into an isolated disposable environment. Disable outbound email, scheduled jobs and production integrations to avoid side effects.
  5. Verify actual records and files—not just that a process starts. Record backup timestamp, elapsed recovery time and anything missing. Protect and later dispose of the test data.

Sources: Hostinger backup and snapshot behavior · Docker persistence and backup. RPO/RTO and the isolated restore procedure are planning recommendations, not provider guarantees.

A playbook has gates, not just commands.

This is a rehearsal outline, not an executable Ansible playbook. Work one stage at a time. Write down the input, change, check and recovery action. Stop when a gate fails; do not keep stacking changes on an uncertain foundation.

  1. Inventory before changingRecord OS/version, IPs, template, current listeners, valuable data, account access and backup entitlement. Gate: you can name what might be destroyed and how to reach provider recovery. Stop: ownership or recovery access is unclear.
  2. Establish recoverabilityExport important data independently; verify current provider recovery points. Gate: restore a harmless sample separately. Recovery: preserve the original server while fixing backup gaps.
  3. Secure administrative accessSet up your named administrator/key and prove a second login before tightening access. Plan and apply supported OS updates. Gate: fresh login works after changes and planned reboot. Recovery: retain the original session and documented console route.
  4. Define the network boundaryList public and private services. Review provider rules, host rules, Docker publishing and IPv6. Gate: an external machine reaches intended ports but not private services. Recovery: revert the rule change using retained access.
  5. Deploy one small workloadReview Compose, image version, secrets, storage and resource use. Start without valuable data. Gate: local response, useful logs and restart behavior are verified. Recovery: roll back the known image/config; database migrations may need their own recovery plan.
  6. Connect a test hostname and TLSUse an unused subdomain, correct DNS authority and a documented proxy/certificate workflow. Gate: external HTTPS works with the correct certificate and renewal is configured. Recovery: retain previous DNS values; remember cached answers can persist.
  7. Observe and alertSet an external check, inspect host metrics, bound log growth and test a notification. Gate: a controlled failure in the test workload produces an alert you receive. Recovery: restart the test workload and verify the recovery notification.
  8. Restore, then repeatRestore the application backup elsewhere, verify its data and measure elapsed time. Record versions and sanitized configuration in source control. Gate: repeat the documented setup on a disposable target without losing data or duplicating services. Recovery: keep the original environment untouched until verified.
Turn practice into infrastructure as code later.

Once you understand the manual sequence, automate it with tools appropriate to the boundary: configuration management for OS state, Compose for application services, and supported provider tooling for resources. Aim for idempotence: a second run should converge to the intended state instead of creating duplicates or destroying data.

Keep the vocabulary consistent.

VPS
A provider-hosted virtual machine with allocated compute, memory, storage and networking.
Host
In the Docker sections, the VPS operating system running Docker—not the provider’s physical machine.
OS / distribution
The operating system and its packaged tools, such as Ubuntu Linux.
SSH
An encrypted remote administration protocol; distinct from web HTTPS traffic.
Firewall
Rules controlling network traffic. Provider, host and container networking can have separate rules.
Port / listener
A port identifies a transport endpoint; a listener is a process waiting for connections on an address and port.
Image / container
A packaged application filesystem and configuration / an isolated process instance created from it.
Compose / Docker Manager
A declarative multi-service format and tooling / Hostinger’s UI for managing container projects.
Volume
Docker-managed persistent storage, separate from a container’s writable layer. Not itself a backup.
DNS / TTL
The naming system used to retrieve records / the permitted cache lifetime of a record.
TLS / reverse proxy
Connection encryption and server authentication / a service forwarding incoming requests to an upstream application.
API / bearer token
A programmatic interface / a credential authorizing its holder to make permitted requests.
Metric / log / alert
A measurement over time / recorded events / a notification requiring attention.
Snapshot / backup
A point-in-time system checkpoint / a recoverable copy. Exact independence, consistency and retention depend on the mechanism.
RPO / RTO
The acceptable recent-data loss window / the target time to recover service.
Infrastructure playbook / idempotence
A documented sequence with checks and recovery / reaching the same intended state safely when repeated.
