Pi factory installation playbook.

Prepare → install → inspect → run one tiny task → reconnect. You execute every step on your VPS.

Companion to Lesson 3 · Ubuntu 24.04 LTS + Windows PowerShell · reviewed 2 November 2026

Not an unattended installer.

Work one checkpoint at a time. Stop at unexpected output and ask your teaching agent. No installation, authentication, crew task or server recovery has been tested on your VPS. Commands below assume Bash on the VPS. Never paste Windows commands into Ubuntu, or Pi slash commands into a shell.

Quick reference · which tool does what?

Pi
Agent runtime; start with pi, authenticate inside it with /login.
FirstMate
Coordinator instructions/extensions; launch Pi from ~/kun-agent-workspace.
Herdr
Persistent terminal workspace; enter with herdr, detach with Ctrl-b then q.
Treehouse
Git worktree/lease lifecycle; separate checkouts, not separate Linux permissions.
No Mistakes / AXI
Required validation/tooling dependencies; not security boundaries. Lavish is presentation-only.

Role explanations and primary sources.

0 · Keep a way back in

  • Confirm you can use the provider’s recovery console. Take a recoverable backup/snapshot before changing the host; a backup you cannot restore is not a recovery plan.
  • Keep your working administrator SSH session open. Test normal command-line SSH before VS Code Remote-SSH. If Windows rejects your SSH config, use the existing repair checklist; do not change firewall settings.
  • Use a new dedicated account named factory, with no sudo, Docker/LXD administration, production keys or unrelated private repositories. A separate account is not a sandbox; world-readable files and network services can still be reachable. Use a separate VM for a stronger boundary. Pi security
  • Do not open HTTP, model, browser-debug or database ports. Only your existing SSH connection is needed for this terminal workflow.
  • Model access costs extra. Choose your provider and spending limits before spawning a crew; a VPS subscription does not include API access.

VPS administrator shell · read-only checks

whoami
hostname
cat /etc/os-release
uname -m
free -h
df -h "$HOME"
getent passwd factory
command -v git gh jq curl node npm pi herdr treehouse || true

Gate: verify Ubuntu 24.04 and note CPU architecture, free memory and disk. A missing factory entry is expected for a new setup. If the account or tooling already exists, stop and inspect it before reusing it—do not overwrite it or blindly upgrade a running factory. There is no universal RAM guarantee: start with one crew and watch free -h. Do not allocate a large crew to a small VPS.

1 · Create a dedicated identity

Already have a suitable dedicated Pi-only account? Confirm its permissions with your administrator, then substitute its name consistently. Do not reuse the Hermes account just because it exists. The commands here create a new account only after checkpoint 0.

VPS administrator shell

sudo adduser --disabled-password --gecos "" factory
id factory
sudo -l -U factory

Gate: the account has no administrator or root-equivalent group memberships and no sudo authorization. A locked password does not prevent public-key SSH. Do not change SSH server settings in this lesson. Ubuntu account management

Windows PowerShell · copy only your existing public key. Replace admin and VPS_IP with your working administrator login and host. These examples select Lesson 2’s vps_learning key explicitly. If yours differs, change both its private-key path for -i and its uploaded .pub path. Do not put a .pub file after -i. If you have no key yet, follow Lesson 2 SSH preparation first. Never copy the private file.

Test-Path "$env:USERPROFILE\.ssh\vps_learning.pub"
scp -o ForwardAgent=no -i "$env:USERPROFILE\.ssh\vps_learning" "$env:USERPROFILE\.ssh\vps_learning.pub" admin@VPS_IP:factory-login.pub

VPS administrator shell · install the public key into the new account only. Check the uploaded file contains the intended public key before continuing.

ssh-keygen -lf "$HOME/factory-login.pub"
sudo chmod 700 /home/factory
sudo install -d -m 700 -o factory -g factory /home/factory/.ssh
sudo install -m 600 -o factory -g factory "$HOME/factory-login.pub" /home/factory/.ssh/authorized_keys

These commands assume the new account’s home is /home/factory; confirm the earlier getent output. Do not run this replacement against an account with existing keys. Verify the server fingerprint through your provider console, not by disabling host-key checks. Ubuntu SSH guide

Windows PowerShell · open a second session

ssh -o ForwardAgent=no -i "$env:USERPROFILE\.ssh\vps_learning" factory@VPS_IP

Do not forward your administrator SSH agent or mount privileged sockets into the factory account. The SSH command above explicitly disables agent forwarding.

Gate: whoami prints factory, echo "$HOME" prints its home, and the original administrator connection still works. Use this new SSH shell for all subsequent user installations.

2 · Install base packages as the administrator

VPS administrator shell only. Review apt’s proposed package changes before accepting.

sudo apt update
sudo apt install git gh jq curl ca-certificates less

Ubuntu packages are sufficient for this introductory GitHub login; if gh is unavailable or too old for the documented commands, stop and use the official GitHub CLI installation instructions. Never give the factory account sudo to fix a missing package.

3 · Install user-owned Node, then Pi

VPS factory shell from now on · no sudo. We use nvm’s user-owned Node LTS installation instead of the guide’s custom npm prefix. This is a deliberate alternative: do not combine nvm with a custom prefix in ~/.npmrc, NPM_CONFIG_PREFIX or PREFIX. If you already configured a prefix, ask for help inspecting it before proceeding; do not delete unrelated settings.

First download the versioned nvm installer for inspection. Reading a script is not proof of safety: you are trusting its publisher and the additional code it downloads. Stop if you cannot establish that trust.

mkdir -p "$HOME/install-review"
chmod 700 "$HOME/install-review"
curl -fsSL https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh -o "$HOME/install-review/nvm-install.sh"
less "$HOME/install-review/nvm-install.sh"

Exit less with q. Only after review, run:

bash "$HOME/install-review/nvm-install.sh"
export NVM_DIR="$HOME/.nvm"
. "$NVM_DIR/nvm.sh"
nvm install --lts
nvm alias default 'lts/*'
node --version
npm --version
node -e 'const [a,b]=process.versions.node.split(".").map(Number); if(a<22 || (a===22 && b<19)) process.exit(1)'

Gate: Node is at least 22.19. If the check exits nonzero, stop. The installer updates your shell profile; reconnect and confirm Node still resolves before proceeding. Do not use set -e with nvm. Node upgrades can require reinstalling global packages. Pi requirements

npm install -g --ignore-scripts @earendil-works/pi-coding-agent
pi --version
mkdir -p "$HOME/.local/bin"
export PATH="$HOME/.local/bin:$PATH"

Open ~/.bashrc with your editor. Add export PATH="$HOME/.local/bin:$PATH" once if missing, for Herdr and Treehouse. The npm package installs under nvm’s Node directory, not ~/.local. Open another SSH session and check command -v node npm pi. --ignore-scripts disables npm lifecycle scripts for this installation; it does not make later agent execution safe. The Pi installer alternative offers a different managed installation; do not mix both routes casually.

4 · Install the terminal and worktree tools

VPS factory shell. The guide’s installer URLs below track current releases, not an immutable course version. Inspect each saved script before execution; record the resulting version. If an installer requests sudo or unexpected permissions, stop. Do not pipe a network response directly into a shell.

curl -fsSL https://herdr.dev/install.sh -o "$HOME/install-review/herdr-install.sh"
less "$HOME/install-review/herdr-install.sh"

After reviewing Herdr’s script:

sh "$HOME/install-review/herdr-install.sh"
mkdir -p "$HOME/.pi/agent"
herdr integration install pi
curl -fsSL https://kunchenguid.github.io/treehouse/install.sh -o "$HOME/install-review/treehouse-install.sh"
less "$HOME/install-review/treehouse-install.sh"

After reviewing Treehouse’s script:

sh "$HOME/install-review/treehouse-install.sh"
npm install -g gh-axi chrome-devtools-axi lavish-axi tasks-axi quota-axi
gh-axi setup hooks
chrome-devtools-axi setup hooks
lavish-axi setup hooks

The AXI helpers provide agent-oriented GitHub, browser, visual review, task and quota commands required by FirstMate’s documented bootstrap. Their setup hooks can modify agent configuration; read output and inspect changes. These hooks do not all target Pi: the browser helper documents Claude Code, Codex and OpenCode hooks, while Pi can use its CLI directly. A successful hook setup is not proof of Pi integration. Lavish is optional for nonvisual work in current FirstMate; we include it to match the linked guide. npm packages may run lifecycle scripts. Install only packages whose publishers and code you trust. Headless VPS: installing browser helpers does not establish that Chrome, display capture or visual review works. The scratch task below uses no browser. Do not expose a remote-debugging port or install a desktop just to pass this lesson.

Correction to the linked guide: install No Mistakes too.

Although the guide calls it optional, current FirstMate requirements list No Mistakes ≥1.46.0 in the universal toolchain. Its PR/CI workflow is deferred, not its installation. Review before executing:

curl -fsSL https://raw.githubusercontent.com/kunchenguid/no-mistakes/main/docs/install.sh -o "$HOME/install-review/no-mistakes-install.sh"
less "$HOME/install-review/no-mistakes-install.sh"

Only after review:

sh "$HOME/install-review/no-mistakes-install.sh"
no-mistakes --version

Gate: No Mistakes is at least 1.46.0. Passing this version check does not demonstrate reviews, remote CI or deployment. No Mistakes source

5 · Review the coordinator workspace

VPS factory shell. Keep the coordinator workspace separate from your projects. The upstream guide deliberately avoids naming its directory exactly firstmate, which can be interpreted as a different mode.

test ! -e "$HOME/kun-agent-workspace" && git clone https://github.com/kunchenguid/firstmate.git "$HOME/kun-agent-workspace"

Gate: if the destination exists, stop and inspect it; do not delete it or continue as though a fresh clone succeeded. Before launching Pi, review this repository’s README, agent instructions, skills and .pi/extensions/ code. Repository instructions can influence tools; extensions can execute code. Trust is a real decision, not a button to dismiss. Record the revision, then configure the reviewed workspace:

cd "$HOME/kun-agent-workspace"
git remote -v
git rev-parse HEAD
mkdir -p config
printf 'herdr\n' > config/backend
printf 'pi\n' > config/crew-harness
cat config/backend config/crew-harness
git status --short

Gate: the two values are herdr and pi. They are Git-ignored local configuration according to the guide; unexpected tracked changes deserve inspection. Keep your project code outside this coordinator repository.

6 · Check tools and authentication

VPS factory shell. Read GitHub’s prompt carefully and use its device/browser login from your own Windows browser if the VPS cannot open one. Do not share the device code. The first exercise needs no remote repository; broad production GitHub credentials are unnecessary. Review scopes and use a low-risk identity. GitHub login documentation

gh auth login
gh auth status
command -v git gh jq curl node npm pi herdr treehouse no-mistakes gh-axi chrome-devtools-axi lavish-axi tasks-axi quota-axi
pi --version
herdr --version
herdr status --json | jq '{version: .client.version, protocol: .client.protocol}'
herdr integration status
treehouse --version
no-mistakes --version

Gate: every listed command resolves, GitHub reports the intended identity, Pi integration is installed, and Herdr reports protocol 14 or newer per the guide. Missing/null fields are not a pass. If protocol is old, review upstream upgrade/migration instructions before changing a running daemon. Use current stable Herdr (0.9.5 at source review): default presentation spaces require at least 0.8.0 in addition to the base protocol floor. Pi native session restoration needs Herdr’s Pi integration version 2 or newer. Protocol 14 does not imply support for every feature. Before dispatch in checkpoint 7, FirstMate’s bootstrap diagnostics must also pass the current AXI version/capability floors and Treehouse get --lease capability check. Do not proceed through MISSING: or OUTDATED: reports. The bootstrap policy is detect → consent → install; grant no blanket permission to install or upgrade. Store credentials only in the tool’s documented private state, never in project files, prompts, screenshots or Git. On headless Linux, GitHub CLI may fall back to plaintext token storage if a secure credential store is unavailable; inspect its warning and protect the account. Storage caveat

7 · Start the coordinator

VPS factory shell · outside Herdr

cd "$HOME/kun-agent-workspace"
herdr

Complete Herdr’s onboarding. The Pi integration installs executable code at ~/.pi/agent/extensions/herdr-agent-state.ts; review it as well as the workspace extensions. In its initial pane, start a fresh pi process (restart Pi if it was running before integration installation). Only approve workspace trust after the review in checkpoint 5. Inside Pi: use /login to authenticate your selected model provider, then /model to confirm the intended model. Complete any provider browser flow on Windows. Credentials belong to the factory user; crew sessions using that user may share provider access. Do not paste them into chat or a repository. Pi authentication

Ask: Confirm the backend and crew harness you detected. Explain how to register a project and run one local-only crew task. Do not edit files, push, create a PR, merge or deploy. Compare its explanation with the upstream workflow. Resolve missing dependencies before a task. Do not enable +yolo or assume automatic per-tool approval. A prompt request is not a security control.

8 · Prove one bounded task, not production readiness

A separate VPS factory shell (leave the coordinator running). Use an empty local repository, with no remote and no credentials. Refuse to reuse a directory that already exists:

test ! -e "$HOME/factory-scratch" && mkdir "$HOME/factory-scratch"

If that fails, stop and inspect the existing directory. Otherwise:

cd "$HOME/factory-scratch"
git init -b main
git config user.name "Factory learner"
git config user.email "factory-learner@example.invalid"
printf '# Factory scratch\n' > README.md
git add README.md
git commit -m "Initialize scratch project"
git remote -v

Gate: initial commit exists and git remote -v is empty. The name/email are local placeholders, not global GitHub configuration. A base commit gives worktree creation a valid starting point.

Inside the coordinator Pi conversation, give the absolute path printed by pwd in the scratch directory. Ask:

Register /home/factory/factory-scratch as my practice project using this workspace’s documented workflow. Work local-only. Delegate exactly one task to one Pi crewmate: create hello.sh containing only printf 'factory ready\n'. Run bash hello.sh and show the output and changed files. No package installs, network operations, pushes, PRs, merges or deployment. Do not enable +yolo. Stop and ask if the task needs anything beyond this scope.

Verify, don’t take its word: identify an actual crew tab and the reported worktree path. In your separate shell, inspect that exact path (do not assume it edited the base checkout):

cd "$HOME/factory-scratch"
git worktree list

Navigate to the listed crew worktree with your shell, then inspect hello.sh in an editor before executing it. After confirming its one-line contents:

git status --short
git diff
bash hello.sh
test "$(bash hello.sh)" = 'factory ready'
git log -3 --oneline
git show HEAD -- hello.sh

Pass: one delegated crew task is visible, the file contains only the requested printf, the command prints exactly factory ready, and the assertion exits zero. Inspect untracked files too: git diff alone omits them, and a committed change requires inspecting the commit. If it only answered in chat, did not delegate or edited the wrong repository, this gate has not passed. Leave the result unmerged; merging is a later lesson.

9 · Detach, then recover the same session

In Herdr, press Ctrl-b, then q to detach—not kill the workspace. Close that SSH client only after detaching. Reconnect from Windows, then run in the VPS factory shell:

cd "$HOME/kun-agent-workspace"
herdr

Gate: find the same coordinator and crew tabs and confirm the scratch history. If the coordinator pane is a shell because Pi exited, run pi -c in the same coordinator directory to resume its latest saved session. Do not launch a duplicate Pi process over an already-running one. Pi sessions · Herdr reconnect instructions

Reboot is different: terminal persistence does not keep processes alive across a VPS reboot, host failure, OOM kill or daemon termination. Saved Pi conversations and Git files may remain, but restarting the coordinator and reconciling crew work is a separate recovery exercise. Current Herdr can restore eligible Pi panes from saved conversation state; that launches new processes, not the old ones. Restored labels alone do not prove workers are alive. No systemd service, boot automation or unattended production work is configured here.

When a checkpoint fails

SymptomNext safe action
SSH/VS Code fails before loginResolve Windows config permissions and command-line SSH first. Keep recovery access; do not weaken host-key checking.
Command not found after reconnectCheck you are factory, then inspect PATH and Bash profile loading. Node/npm/Pi use nvm; Herdr/Treehouse usually use ~/.local/bin. Do not reinstall with sudo.
nvm reports prefix conflictInspect existing ~/.npmrc and prefix environment variables with the teaching agent. Do not expose registry auth tokens while sharing output.
Trust prompt or hook behavior differsPause and compare the reviewed checkout revision to current upstream documentation. Do not approve unknown executable extensions just to continue.
Protocol/integration check failsInspect Herdr version, protocol and integration status before launching crew. A newer CLI alone may not upgrade a running daemon.
Browser helper fails on headless VPSReport browser tasks as unverified. The scratch shell exercise does not require them; do not expose a debug service.
Crew cannot log in or consume model accessConfirm same Linux user and provider setup without sharing credentials. Check provider quota and limits; do not start more agents.
VPS slows or a process disappearsCheck memory/disk; stop additional crew work. Investigate possible OOM termination with your administrator rather than blindly retrying.

Pause/cleanup: detaching leaves agents running and able to spend quota. Before a long break, use the workspace’s documented stop/quit controls and confirm no crew is still working. Preserve scratch work and sessions until inspected; do not use broad process-kill or recursive-delete commands. If abandoning the setup, revoke unused GitHub/provider authorizations through their account settings. Rotating an exposed credential comes before cleaning Git history.

Bring back evidence, not secrets

Start with checkpoint 0 only. Tell your teaching agent: confirmed OS/architecture, approximate available memory/disk, whether factory already exists, and whether SSH plus recovery-console access work. Later report tool versions, Herdr protocol/integration status, scratch-task result and reconnect result. Redact host/user details if desired. Never share tokens, private keys, device codes, full config files or session exports.
