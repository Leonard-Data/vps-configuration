Manual service playbook.

Install once, inspect first, and update one service at a time.

Reference for Lesson 5 · reviewed primary sources, learner-run checkpoints

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Checkpoint 0 — inventory before installation

Use the account that already owns each service. Open a separate SSH session for each runtime account; a user service needs the owner’s login session. If the inspection command is missing, record that result; do not run the next mutation. These paths match the course defaults, not a verified server.

Private service record — fill once per service
FieldEvidence to record
IdentityService, owner, install method/path, current version, Git commit/image digest where relevant
Desired stateExact target or documented channel policy, release notes, reason for changing
OperationStartup owner, process/service name, harmless health check, maintenance window
RecoveryState/config/key locations, backup time and private location, tested restore evidence, previous known-good version

Keep secrets and exact private backup locations out of a public repository. A secret-free version list can go in Git: a row per service, with current, desired and verified values kept distinct. Do not label desired as deployed until checks pass.

VPS — Hermes owner

whoami
command -v hermes
hermes --version
hermes doctor
# Default course checkout only; substitute your inspected path.
git -C "$HOME/.hermes/hermes-agent" rev-parse HEAD
git -C "$HOME/.hermes/hermes-agent" status --short
hermes update --help

Pass: installation provenance and state locations are understood. Current upstream update flags may not exist on an older installation. Match instructions to installed --help before proceeding. A dirty checkout needs an independently protected copy of local work, not a blind reset. Official installation layout

VPS — Pi’s factory owner

whoami
command -v node npm pi
node --version
npm prefix -g
npm list -g --depth=0 @earendil-works/pi-coding-agent
pi --version

Pass: the active Node and npm prefix belong to factory’s intended nvm installation. The course requires Node 22.19+; check the target release’s requirements too. A managed Pi install is a different route: do not replace it using npm commands. Pi customization packages, FirstMate/Herdr/Treehouse and their compatibility are separate version records. Pi’s official repository · Factory compatibility checkpoints

VPS — n8n Compose operator, original project directory

pwd
docker compose version
docker compose config -q
docker compose ps
docker compose exec -T n8n n8n --version
docker compose images n8n

Pass: you recognize the original project name, resolved volume and running version. Check mounts with your container inspection tooling and record the actual volume identity privately. Docker access is effectively host-administrator access; do not give it to Hermes/Pi or a generic CI runner. Avoid docker compose config without -q in shared logs: interpolation may print secrets. Compose config validation

Checkpoint 1 — install only what is missing

Manual setup already has full staged recipes. Use only the route matching your inventory:

  • Hermes setup step 4: dedicated user, reviewed official installer, provider setup and a harmless reply.
  • Pi setup: Node then factory tools: dedicated user, nvm, exact compatible tooling and scratch workspace.
  • n8n setup checkpoint 0 onward: Compose + Caddy, private n8n, restricted owner setup and dummy workflow.

Do not run a new installer over a working but unidentified service. Do not run a second copy on the same data. Check the troubleshooting table if a prerequisite fails.

Checkpoint 2 — one protected change

Read release notes and migration warnings. Choose a maintenance window. Pause the affected agents/jobs, capture a coordinated backup, copy it encrypted off-server and rehearse in isolation using the recovery playbook. Require independent SSH/recovery access and free disk space. If any check fails, stop. A backup command finishing is not a restore test.

Hermes — managed update, not a universal exact-version pin

The supported updater manages code, dependencies and gateway restart ownership. After confirming flags in installed help, current upstream installations can inspect hermes update --plan and hermes update --check. The check can fetch metadata and write locally; it is not a zero-write audit. After protecting all required state, use:

# Hermes owner; maintenance window; backup/rehearsal already completed.
hermes update
hermes --version
hermes doctor
# Only if you configured a gateway:
hermes gateway status

Latest upstream source installs normally select a stable release; verify the actual channel and target before accepting. hermes update --backup is available in current docs, but its archive exclusions and runtime scope still need review. It is not a substitute for your recovery set. Inspect update warnings, the actual resulting commit and, where supported, hermes pm status and ~/.hermes/logs/update_receipts/latest.json. A successful exit can still report follow-up restart/build work.

Exact revision requirement? Do not invent hermes update --version or a rollback flag. Follow the selected release’s source-maintenance procedure and compatible bootstrap/runtime; current PM-managed checkouts are not maintained by bare pip install. Ask for a version-specific rehearsal before automating this branch. Official updating and manual source maintenance

Pi — select an exact npm version

Only for the existing npm/nvm route. Stop affected crews and preserve agent state plus project/worktree state first. Keep Node unchanged during this step. Choose a published version from reviewed release notes; do not copy a tutorial’s old number.

# factory owner, intended nvm Node active; replace this value first.
TARGET_PI='REPLACE_WITH_REVIEWED_PUBLISHED_VERSION'
if [[ "$TARGET_PI" == REPLACE* || -z "$TARGET_PI" ]]; then
  echo 'STOP: choose a reviewed Pi version' >&2
else
  npm install -g --ignore-scripts "@earendil-works/pi-coding-agent@$TARGET_PI" &&     pi --version
fi

Pass: Pi reports the selected version and can perform one harmless scratch task; factory integrations satisfy their existing compatibility checks. This pins the top-level npm package, not the entire transitive dependency tree. No sudo, no custom npm prefix. Pi 1.4 documentation distinguishes pi update (runtime), pi update --extensions and pi update --all; check the installed help because old versions differ. The unqualified update route does not retain your chosen older version. Pi release notes

n8n — change only the selected image

In the original project directory, preserve the same project name and volume. Privately edit only N8N_VERSION in the existing .env to an exact reviewed stable tag, after reading release notes and rehearsing its migrations. The course’s modern lab requires 2.35.0+; older deployments need a version-specific migration plan. Do not change Caddy, the key, the domain or Compose topology in this update.

# Run each line separately and stop at the first error.
docker compose config -q
docker compose pull n8n
docker compose up -d --no-deps n8n
docker compose ps
docker compose exec -T n8n n8n --version

Pass: the selected version is running, HTTPS login works, previous dummy workflow data remains, a dummy credential decrypts and a harmless manual workflow succeeds. Use your normal container inspection tooling to record the running image ID/digest; tags can be moved by publishers. Inspect recent local logs privately if unhealthy; logs can contain sensitive execution data. Never use down -v or volume pruning here. Container replacement preserves named volumes; it does not protect you from database migrations. n8n update policy · Compose up behavior

Checkpoint 3 — record only what you proved

Record before/after versions, exact change, backup/restore evidence and health-check results. Leave failures visible. Ask your teaching agent follow-up questions with service, owner, installation method, last passing checkpoint and a redacted error—not environment files, logs containing credentials or private keys.
