Service recovery playbook.

Keep the failed state. Restore a compatible set. Prove safety before cutover.

Reference for Lesson 7 · offline lab first, production recovery separately reviewed

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Recovery vocabulary — decide before an incident

RPO — recovery point objective
The maximum acceptable amount of recent data loss, expressed as time. A daily backup may lose nearly a day’s changes; an untested backup may lose much more.
RTO — recovery time objective
The target time to restore useful service. Measure the whole drill, including fetching backups and regaining access, not only extraction time.
Recovery set
Compatible application/runtime version plus coordinated state, configuration, encryption keys, permissions and deployment identity.

For the lab choose your own RPO/RTO and write them down. These are objectives, not guarantees made by a provider. Keep an off-server encrypted backup plus separately usable decryption/recovery access. Do not store the only key on the VPS you are trying to recover.

Checkpoint 1 — start with the offline n8n drill

  1. Use only the course’s dummy SQLite lab. Note the original project and original volume identity; verify that your recovery destination is different and empty.
  2. Follow the existing guarded backup / offline restore recipe: stop writes, capture volume plus private configuration, checksum and transfer off-server encrypted. Check every command’s result; do not live-copy SQLite.
  3. Restore into the guarded n8n-restore destination. Keep the original volume untouched. The recipe does not start the restored service and uses one-off CLI reads, not webhook/schedule workers.
  4. Verify the archive checksum, workflow read and dummy-credential decryption using the matching image/key. The recipe sends decrypted export to /dev/null; never write plaintext credentials to Git or logs. With no dummy credential, the decrypt check proves nothing.
  5. Record elapsed time, data timestamp, image identity and check results privately. Failure is useful evidence—do not claim success merely because extraction completed.

Scope: this offline drill validates a small part of recoverability, not HTTPS, full automation or a production cutover. It may share the lab VPS for dummy data, but a real-data drill requires a separate network-isolated host. Before any normal restored startup, block outbound contact and inbound webhooks and disable restored schedules/triggers. Avoid duplicate agent/gateway instances too. Then test only harmless manual behavior. Ask for a topology-specific plan before starting real restored automations.

Checkpoint 2 — if a live update fails

  1. Freeze changes. Pause CI delivery and stop the affected runtime/triggers using its documented owner/manager. Preserve administrator recovery access. Stop only the affected service, not the whole host by reflex.
  2. Preserve evidence. Save redacted diagnostics and a protected copy of failed current state. Avoid destructive pruning, resets, reinitialization and repeated restarts.
  3. Choose forward fix or coherent restore. Check the release’s migration/rollback guidance. Changing only the image or package is safe only if data compatibility is explicitly established.
  4. Restore separately and verify. Recover the compatible pre-update set into separate isolated storage. Check permissions, data, credential use and application health; do not overwrite production to find out whether the archive works.
  5. Approve the loss and cutover. Identify changes since the backup and any external side effects that cannot be undone. Agree the loss window, fence the old instance, then execute a separately reviewed cutover. Resume schedules only after checks pass.
  6. Reconcile desired state. Update the reviewed Git target/receipt so the next pipeline does not redeploy the failure. Keep preserved evidence until recovery is accepted.

For Hermes, use the documented release-specific source/bootstrap and state procedure; do not improvise git reset --hard plus dependency commands. For Pi, stop old crews and confirm no duplicate processes before pi -c in the original working directory. For n8n, a migration may require the old database and original encryption key with the old image, not a container-only rollback.

Checkpoint 3 — a recovery receipt

Write: scenario, service/version, backup timestamp, private backup location, verification results, actual data-loss window, elapsed recovery time, blocked side effects and unresolved gaps. Compare measured results with RPO/RTO. Keep the receipt secret-free if sharing it.

Ask your teaching agent follow-up questions about the first failing checkpoint. A completed lesson is not evidence of a restore; bring back the redacted receipt before recording demonstrated learning.
