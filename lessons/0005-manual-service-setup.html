Manual First: know what you run.

Before automating an update, make one service change understandable and repeatable.

Lesson 5 · 7 minutes · inventory exercise: 10–15 minutes

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Recall before you touch the server

From memory: why is a volume not a backup? What is the difference between your administrator account and the Hermes/Pi runtime accounts? If unsure, revisit safe access.

One habit; three installation types

Know the current state → choose a target → protect data → change one thing → prove it works. “Install everything latest” skips most of that habit.

What you are maintaining
ServiceVersion identityState is separate
HermesReported release + source commit + update channelPrivate home, profiles, credentials and gateway data
PiExact npm package version + Node versionAgent sessions/auth, projects and customization packages
n8nExact image tag, preferably recorded digestDatabase, encryption key, configuration and binary data

A pin means a selected version rather than a moving target. A release tag is readable; an image digest identifies content. A Git commit identifies source, not every downloaded dependency. Pinning is not permission to ignore security updates. Docker digests

Your win: one service record

  1. Open checkpoint 0. Inspect one service under its existing owner. Do not install missing software yet.
  2. Privately record owner, installation method/path, current version, target version, persistent state, health check and backup evidence. Record “not installed” rather than guessing.
  3. If new, use the existing Hermes, Pi or n8n setup route. Do not reinstall a working service using a different method.
  4. Use the matching manual-update checkpoint only after a protected backup and isolated rehearsal. Keep OS/Node/proxy upgrades out of the same change.

Pass: you can identify which version is actually running, where its data lives and how to test it without a real side effect. A saved inventory alone does not prove deployment or recovery.

Troubleshoot without digging a deeper hole

command not found often means wrong user/PATH, not “install again as root.” A package permission error is not permission to use sudo npm. A 502 can be an unhealthy upstream, not broken TLS. Use the symptom → check → safe response table before changing anything else.

Retrieve, then check

1. Which record identifies the running service?

Answer key and reasoning

Inspect the installed version under its actual runtime owner. A planned target is not evidence of a completed change.

2. Your Pi update fails with EACCES. What next?

Answer key and reasoning

Inspect the installation owner and npm prefix first. Do not bypass account separation or mix npm installation methods.

3. What belongs before an n8n update?

Answer key and reasoning

Protect and rehearse restoring the matching data, key, configuration and version before changing the live service.
