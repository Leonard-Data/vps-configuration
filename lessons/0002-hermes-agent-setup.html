Give Hermes a safe home.

Connect from Windows, run Hermes as an ordinary Ubuntu user, then learn what belongs in Git—and what must stay out.

Lesson 2 · 10-minute explanation · practical setup: allow 45–90 minutes, plus an optional CI/CD lab

This page does not configure your VPS.

You reported Ubuntu 24.04 LTS. Its resources, current accounts and firewall have not been inspected. The commands live in the linked playbook, with stop points. We assume Nous Research’s Hermes Agent, not another product named Hermes.

First, retrieve one idea.

Before reopening Lesson 1: what is the difference between connecting by SSH and visiting a website? Say it aloud. SSH gives you a server shell; it does not require publishing a web application.

Three places, three jobs

Your Windows computer
PowerShell runs your SSH client. Your private login key stays here. VS Code can edit a remote project through the same SSH connection. VS Code source
Your Ubuntu VPS
Runs Hermes and stores its private credentials and state under the Hermes user’s home. An administrator prepares the machine; the hermes account runs the agent without sudo privileges.
Your GitHub repository
Stores reviewed, non-secret instructions and deployment examples. It is neither a backup of the whole VPS nor the agent’s private home. GitHub Actions can check a commit and send one approved file to the server.

The goal is not to fork and redeploy the entire Hermes application on every push. Use the official installer/updater for Hermes itself. Your small hermes-ops repository manages your own instructions. Official update methods

An SSH key is a pair, not a password to paste everywhere.

Your public key goes in the server’s authorized_keys. Your private key proves you own it and must stay private. A passphrase protects your personal private key if someone steals the file. Ubuntu’s SSH guide

Two different checks happen.

Your key proves your identity to the server. The server’s host key proves its identity to you. Compare its fingerprint with the provider’s recovery console before accepting a first connection. Never solve a host-key warning by blindly disabling checking.

A local permissions error happens before the VPS.

If Windows OpenSSH rejects ~\.ssh\config because an unrecognized SID has access, fix that local file’s permissions first. In this case, VS Code’s UnparsableOutput is only the follow-on error, not a server setup failure. Follow the Windows config repair and two verification gates: local config evaluation, then a real command-line SSH login, before retrying Remote-SSH. Do not open firewall ports or weaken SSH checks to solve it.

Using another computer? SSH keys and config belong to each local machine/account. Give the new computer its own personal key, append only its public key on the VPS, and verify the server fingerprint again. Do not replace existing authorized keys or carry Windows permissions across accounts. Follow the other-machines checklist, including what changes for another VPS or a macOS/Linux client.

Later, CI uses a separate deployment key. It is restricted to replacing one instruction file; it must not be your personal administrator key. Your GitHub account authentication is a third, separate concern.

Your first tangible win: one safe conversation.

  1. Open the requirements checkpoint. Confirm recovery access before changing accounts.
  2. Follow PowerShell SSH setup. Test a second connection while the first remains open.
  3. Follow the non-root installation. Configure a paid/API-backed or supported subscription provider; the VPS does not include model access.
  4. Start Hermes and ask: “Explain the difference between a public SSH key and a private SSH key. Do not execute tools.” Check the answer against the explanation above.

Stop here for today if this was new. Do not add a messaging bot or automation until ordinary SSH and a simple Hermes chat work. With a local terminal backend, agent tools can act with the account’s permissions; prompt wording is not a security sandbox. Use a dedicated account without access to unrelated production data. Configuration and tool backends

CI checks. CD delivers.

Continuous integration (CI) checks a proposed change. Continuous deployment (CD) applies a change automatically after its gates pass. With a manual approval gate, this lab is more precisely continuous delivery; the file transfer after approval is automated.

  1. Edit SOUL.md in your development project.
  2. Push a branch and open a pull request. CI checks the file’s format.
  3. Review the actual instructions, then merge to main.
  4. Approve the protected production deployment. Actions sends only SOUL.md.
  5. Open a fresh Hermes conversation and test the change; restore the previous file if needed.

SOUL.md defines Hermes’s primary identity and replaces its default identity. It is powerful configuration, not an innocent note. The lab keeps credentials, sessions, memory and the installation out of Git. A passing format check is not a safety review or proof that the agent behaves correctly. Context-file source

Ready later? Follow the repository steps and optional deployment lab.

Close the explanation. Retrieve the boundaries.

1. Which item belongs in the VPS authorized_keys file?

Answer key and reasoning

Your public login key. Never upload the private half to the VPS or put it in the repository.

2. Which file is this lab designed to version and deploy?

Answer key and reasoning

Reviewed agent instruction file. Ignore rules help avoid accidents but do not remove a secret already committed to history. Revoke a leaked credential first.

3. A new SSH key is installed. What comes before closing your existing administrator session?

Answer key and reasoning

Verify another key login. Keep a known working session and provider recovery access. Hardening must not strand you outside your own server.

Explain where each belongs: your private SSH key, a public SSH key, a model token, and SOUL.md. Then explain why CI passing does not prove Hermes is safe or healthy.
