CI/CD: automate the checked path.

Automation repeats your operating procedure. Make sure it repeats the safeguards, too.

Lesson 6 · 7 minutes · first gate rehearsal: 20–30 minutes

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Recall the manual contract

Without opening Lesson 5, name the evidence you need before and after an update. If you cannot yet update one service manually, CI/CD is not the next command to run.

Check, approve, deliver, verify

  1. Git changeReview a target version and procedure.
  2. CICheck files without VPS secrets.
  3. ApprovalReview backup and rehearsal evidence.
  4. CDRun a bounded deployment; verify health.

Continuous integration (CI) checks changes. Continuous delivery keeps a checked release ready for a human-approved deployment; this course does not choose unattended continuous deployment. A green YAML check is not proof of a healthy VPS.

Use one version inventory, but separate deployment procedures: Hermes has a managed updater and source state; Pi has an npm/Node boundary; n8n has database migrations. No universal “SSH then update everything” script.

Your win: reject an unsafe change

Imagine a pull request that changes n8n:2.x.y to n8n:latest, adds a real encryption key, and promises “automatic rollback.” Before opening the answer, identify three reasons not to deploy it.

Feedback

The target is moving, the key is exposed, and a database migration may prevent a simple image rollback. Stop delivery, remove the secret from the change and rotate it through an application-aware plan if exposed. Git history removal alone does not revoke a secret.

Follow the CI/CD playbook to define checks, validate your approval gate and trace an annotated workflow. The working restricted SOUL.md lab remains a configuration-only exercise, not an application upgrader.

An approval button is not the whole gate

Configure required reviewers on the GitHub environment, then prove a deployment job waits and cannot read its environment secrets before approval. workflow_dispatch means “start manually,” not “independently approve.” Private-repository reviewer support depends on the plan; if unavailable, keep manual deployment. GitHub availability and protection rules

For SSH failures, pending jobs, version drift and partial deploys, use the CI/CD troubleshooting table. Never bypass host-key checking to make a job green.

Retrieve, then check

1. What does a successful CI syntax check prove?

Answer key and reasoning

A syntax check proves only its tested condition. Runtime behavior, backups and recovery need their own evidence.

2. What gates this course’s production delivery?

Answer key and reasoning

Required environment approval gates the deployment job. A manual launch alone is not a required-reviewer gate; verify plan availability.

3. What should the deployment SSH key permit?

Answer key and reasoning

A restricted key invokes one reviewed operation under a limited account. Its handler must validate requests and protect application state.

Rehearse the stop path

Tomorrow, explain CI versus CD from memory. Then describe what happens if CI passes but backup verification fails: deployment must stop. Ask your teaching agent follow-up questions before adding deployment credentials.
