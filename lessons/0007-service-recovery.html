Recovery: prove you can get it back.

A recoverable service is more than a running image and a file named backup.

Lesson 7 · 7 minutes · offline drill: allow 30–60 minutes

You run the setup; this page changes nothing.

Use a disposable lab and dummy data. Installed versions, service ownership, recovery access and backups are unverified. Stop at the first failed checkpoint; do not paste secrets into chat.

Recall what a version pin cannot save

You replaced n8n’s container. Its new version migrated the database. Can selecting the old image safely undo that change? Explain before reading on.

Recover a coherent set, not one file

Version rollback changes code or an image. Data restoration replaces state from a prior backup. They are different operations. If a migration changed the data, older code may not understand it. A code rollback is not a general undo button. Hermes rollback compatibility warnings

Minimum recovery questions
ServiceWhat must agree?What must stay stopped?
HermesCompatible release/runtime, private state, profiles and credentialsGateway, scheduled tasks and duplicate agents
PiPackage/Node versions, agent state, projects and customization versionsOld crews and duplicate task execution
n8nCompatible image, database, original encryption key and binary dataRestored schedules, webhooks and external writes

The backup must live independently of the failed VPS and be decryptable using recovery access you still possess. A provider snapshot or a checksum alone is not proof of a usable application restore. Hostinger backup and whole-server restore scope

Your win: choose the safer recovery

Your n8n upgrade fails after migration. You have yesterday’s off-server database, key/configuration and image identity, plus today’s broken volume.

  1. Pause delivery and stop the affected runtime. Preserve today’s state for diagnosis; do not delete it.
  2. Restore the coherent pre-update set to separate storage on an isolated test host.
  3. Block external traffic and disable restored triggers before any normal service startup.
  4. Verify data reads and dummy-credential decryption; then run only a harmless manual workflow.
  5. Decide how much recent work would be lost before a separately approved cutover.

Start with the offline drill. It is deliberately smaller than a production recovery. The playbook also covers Hermes and Pi state.

Successful extraction is not successful recovery

Credentials may fail because the key does not match. An empty installation may mean the wrong volume/project. A resumed crew may repeat work already running elsewhere. Use the recovery troubleshooting table before retrying.

Retrieve, then check

1. What should you restore after an incompatible migration?

Answer key and reasoning

Restore compatible application code and the coordinated pre-update state, key and configuration. Preserve the failed state separately.

2. What does a matching archive checksum demonstrate?

Answer key and reasoning

Checksums verify the transfer against the recorded copy. They do not prove the database is usable or the workflow safe.

3. Where should your first recovery drill run?

Answer key and reasoning

Use separate storage and preferably a separate network-isolated host; prevent restored automations from contacting real systems.

Come back with evidence, not confidence

Tomorrow, list the recovery set from memory. In a week, repeat a small isolated restore without relying on yesterday’s terminal history. Ask your teaching agent follow-up questions with elapsed time, the last successful check and any redacted error.
